# XSwift 退役能力分析与实施计划

> 验证日期：2026-10-29；退役范围更新：2026-10-30
> TT 基线：`4ba6c6c`，仓库 `/root/dl/TTorch`
> 核查对象：本机实际安装的 `xswift_ext`、Swift、mcore_bridge、TE，以及四卡真实训练证据。
> 性质：现状分析、能力清单与后续实施建议；不是已完成迁移的交付报告。
> 验证已覆盖全部 15 项功能，并新增三组真实 Qwen 四卡训练，每组 6 步、两次评估。仅增加独立验证脚本与证据，没有修改 TT 核心/框架包/插件，没有卸载 XSwift。完整矩阵、复跑方式和未覆盖边界见 §13。

## 0. 结论与退役定义

**用户决策（2026-10-30）：XSwift 厂商预热功能全部放弃，不迁移、不补齐。** 包括厂商 Megatron/HF/DeepSpeed 首批填充、CP/SP 预热扩展、dummy token 随机化与位置整理、text/视觉 `warmup_padding_mask` 注入及其转发。相关缺口退出实施队列与退役等价验收，只保留历史分析和实测数据；“放弃”不是“已支持”。

本机 Swift 的 `SWIFT_PAD_WARMUP` 属于已存在的独立策略，本次不删除、不改变其配置，也不将其扩展列为 XSwift 退役要求。本轮仅调整迁移范围，没有修改 site-packages 或卸载插件。15 项/18 个接口仍用于历史盘点，不再作为要求全部等价迁移的覆盖率分母；一般 packed/CP、原生 router mask、视觉输入与 THD RoPE 契约仍按正常训练能力验收。

**当前 dense Qwen 的训练主流程可以关闭 XSwift 运行，但尚不能宣布 XSwift 全部能力已由 TT/原框架覆盖，更没有完成“卸载 XSwift 后功能无退化”的验证。**

**文档主线：XSwift 做了哪些优化/兼容处理 → TT 流程哪些已经支持 → 哪些尚未支持 → 从尚未支持的部分按优先级逐项完善。**

以功能名称为唯一分析单位，不再使用“接口编号”和“能力编号”两套代号。一个功能可以修改多个接口；接口清单只用于追溯实现，不作为独立工作项，也不按接口数量计算覆盖率。

| XSwift 做的优化/功能 | 原作用与适用场景 | TT 流程当前支持状态 | 当前支持者/缺口依据 | 尚需完善的部分 | 优先级 |

| Embedding object payload CPU gather | 避免普通分布式对象序列化设备 Tensor 的兼容问题 | 原路径当前可用；缺CPU保护 | 两卡FP32/BF16原/保护loss与本地dgrad逐位一致 | 跨设备反序列化与其他后端仍待覆盖 | 暂缓：本机未复现 |

| DCP stub 返回契约适配 | 避免 bool/error-list 接口版本不匹配 | 当前版本兼容与小状态恢复通过 | 原/厂商均bool；实际DCP save/load模型/optimizer张量精确一致 | 不搬恒真stub；未验证TP/EP分片完整校验 | 已替代：退出新增实现队列 |

**工作队列只来自“未支持”及“部分支持的未闭环部分”。已有框架实现优先复用和验证，不因它不在 TT 目录就重新实现。**

P0 优先修正确性与参数存储风险；P1 补常用流程、显存保护与未兑现优化；P2 补观测。具体场景是否启用决定该项是否触发，但完整退役清单中不得把未启用写成已支持。

详细分析使用同一功能名称；§2 的每个接口直接对应本表功能，§9 也按功能名称列推进顺序。

### 0.1 三个不同的完成层级

| 层级 | 含义 | 当前结论 |
|---|---|---|
| 插件关闭 | `XSWIFT_PLUGIN_ENABLE=0`，不走自动初始化 | 指定 dense Qwen 四卡配置已验证 |

### 0.2 本文范围

本文只评估 **XSwift** 退役。默认保留：

- Swift / Megatron Core / mcore_bridge；
- torch_xmlir 的设备对接及算子提供；
- 当前厂商 TE、HydraX、通信和 xpu_fla 基座。

- loss 最大绝对差：约 `0.001337`；平均绝对差：约 `0.000377`。

### 3.2 TT 已有、但不等同于 XSwift 替代的能力

- 设备、Stream/Event、显存查询、随机等 torch.cuda 门面纳管。
- 标准/zcg 独立 RMSNorm provider；四卡每 rank 接管 18+13 个模块。
- Megatron SwiGLU、Bias-SwiGLU、BSHD RoPE 的函数分发登记。
- `mcore_bridge.get_mcore_model` 的环境变量门控建模包装。
- 测试专用 callback 的逐步计时、输入指纹与 provenance；不是生产 profiler callback。

这些不能替代：

- 调用方缺失的 Stream 围栏；
- 专家参数存储/转换/merge 契约；
- CP/THD fallback 参数契约；
- MoE dummy-token 路由 mask；
- 评估期间厂商策略切换；
- 完整训练恢复和在线观测。

### 3.3 当前框架已提供

- Swift 基础训练日志、显存、耗时与剩余时间。
- 当前安装 Swift 的 Megatron pad warmup 与 communicator warmup。
- 当前版本 Swift 自身的特定 Conv3d workaround。
- 基本 LoRA、重计算、并行、optimizer、attention 等由框架和仍在场的厂商基座提供。

不要为去掉一个插件复制整套训练框架；也不要把“仍由框架/厂商基座提供”误记为“TT 已重新实现”。

## 4. 必须优先补齐的正确性能力

### DDP 初始化跨流同步

**状态：缺少显式双向流依赖；本机 P800 已做专项验证，未复现数据竞争。属于跨后端兼容风险，不能表述为当前训练已发生错误。**

当前 Swift 在新 Stream 上构建 DDP，但没有与默认/当前流的双向依赖。XSwift 显式执行：

1. 新流等待当前流，确保参数初始化已经完成。
2. 在新流上构建 DDP。
3. 当前流等待新流，确保后续 broadcast/forward 不抢跑。

TT Stream 门面只转发底层能力，不会补调用顺序，因此不是等价覆盖。

**2026-10-29 本机专项实测：**

### THD RoPE fallback 保留 CP group

**状态：本机已稳定复现，根因确认；生产修复尚未实施。与 DDP 不同，这是当前安装栈中可直接触发的参数契约错误。**

mcore_bridge 包装器 pop 掉 `cp_group`，非 batched fallback 没有传给捕获的原函数。当前 Megatron 原 THD 函数要求 `cp_group` 非 None。

XSwift 能识别 closure 中捕获的原 THD 实现，向 fallback 保留 group；无显式 group 时从 parallel_state 获取。

#### THD 是什么，哪些输入触发错误

`THD` 表示 packed token 数 T、attention head 数 H、head dimension D；多条变长序列沿 T 拼接，`cu_seqlens` 保存各序列边界。CP group 给出当前 context-parallel 分组的 size/rank，用于选择每条序列上属于本 rank 的旋转位置。即使 CP=1，当前 Megatron 原函数也要求一个非空 group，不接受用 None 表示单卡。

当前 bridge 用 `freqs.shape[0] == (cu_seqlens // cp_size)[-1]` 判定 batched RoPE：

- 相等：频率已经覆盖本 rank 整个 packed token 流，直接转到 BSHD 计算，不调用原 THD fallback。
- 不相等：例如频率只提供“最大单条序列长度”的传统 RoPE 表，需要原 THD 按各序列及 CP rank 取位置；此分支漏传 group，确定报错。

#### 本机复现矩阵与输入

2026-10-29，保持同机 P800 环境，XSwift/XME 自动初始化关闭；xmlir、TT 分别使用 CP1 单 rank 和 CP2 两 rank 的真实进程组，在四个独立 torchrun 启动中验证。TT 显式激活且 `TT_RESTORE_VENDOR=perf`；没有开启全套 XSwift 插件。对照仅在独立测试进程内将私有 THD 函数临时换为 XSwift 的 THD-only wrapper，每个 case 后恢复。

| 调用者没传 group | 显式传真实 group 仍报错；公共入口默认 group 也报错 | 排除为必要原因 |

#### 为什么之前 Qwen 四卡能运行

之前实际保存的 TT 训练 `args.json` 已核对：`padding_free=True`、`context_parallel_size=1`、`apply_rope_fusion=False`，不是“默认 fused THD 绕开错误”。Qwen3.5 MRoPE 按输入 position IDs 生成整段频率，若频率长度等于 packed 本地总长，就进入已验证正常的 batched 分支，因此非 batched 缺口不会触发。

这是由实际配置和源码条件支持的解释；之前训练没有逐次记录 THD 频率形状，本轮也未重跑 Qwen，所以不宣称已证明每次历史调用的分支。还确认 bridge TransformerLayer 在 unfused attention 期间会临时覆盖 BSHD 符号，TT 的 BSHD 绑定成功不能当作该次调用命中的证据；该行为作为其他性能项线索记录，不在本轮顺手修改。

#### 修复位置归属分析（2026-10-30，用户已确认）

**结论：根治应改 `mcore_bridge/patcher.py` 的 `_patch_mrope()`，不在 Swift 训练对接层，也不改 Megatron 本体。** 这是 bridge 自身的参数转发缺陷，不是 XSwift 独有能力。

| 层级 | 位置 | 当前行为 | 是否本次错误来源 |
|---|---|---|---|
| Swift 训练对接 | `swift/megatron/trainers/*` | 组织训练流程与模型调用，不直接构造 THD 的 `cp_group` | 否：无证据表明它漏传 |
| Megatron 公共入口 | `rope_utils.apply_rotary_pos_emb:250-266,308-311` | `cp_group is None` 时取当前 CP group 再传给私有 THD | 否：行为正确 |
| **bridge THD 包装** | `mcore_bridge/patcher.py:200-213` | `pop('cp_group')` 后用于算 `cp_size`，fallback 调原函数时未传回 | **是：根因所在** |
| Megatron 原 THD | `rope_utils._apply_rotary_pos_emb_thd:178-204` | 需要 group 取 size/rank；为 None 时显式报错 | 否：报错是在暴露上层缺陷 |

**`pop()` 本身有其目的，不能简单改成 `get()`。** batched 分支转调的 `_apply_rotary_pos_emb_bshd`（`rope_utils.py:92-98`）签名没有 `cp_group`，保留该键会触发 unexpected keyword。真正的缺陷是两条分支共用同一份被删键的 `kwargs`，fallback 未按原函数契约补回。“`pop` 是为 BSHD 服务”由函数签名推断，未查提交历史确认作者意图。

| 候选修复位置 | 评价 |
|---|---|
| **`mcore_bridge/patcher.py`** | **首选**：在参数丢失发生处修正，两条分支契约集中维护，不新增依赖 |
| Swift/XSwift 外层 wrapper（现状） | 仅受限兼容：重复分支判断、依赖 `inspect.getclosurevars` 查闭包、受导入与绑定顺序影响；闭包查找失败时退回原 bridge，**不保证修掉该错误** |
| Megatron 原 THD 自动兜底 | 不合适：把 `None` 兜成全局 group 会掩盖 bridge 丢弃调用者显式 group 的问题，兜到的 group 也不一定是调用者原本指定的那个 |

关键原则：**不能用“重新获取一个默认 group”代替“保留调用者明确指定的 group”**，否则报错消失但分组语义仍可能错。

bridge 内最小修法：显式传入的 group 用于算 `cp_size`，fallback 时把**同一个对象**传给原 THD；batched 分支继续不传该键；需要 fallback 且 group 缺省时再解析真实 CP group，不给原本可用的 batched 分支增加新前置要求。不需要取消 `pop()`、不改 batched 判定条件、不重写 RoPE 计算。

交付方式与逻辑归属分开：能维护或向上游提交 `mcore_bridge` 时直接修源头并走受控版本发布，不以手改 `site-packages` 为最终交付；暂时不能改依赖时，TT 可提供针对受影响版本的 bridge 兼容修补，但须标注临时兼容、不放进性能 provider、不依赖 `xswift_ext`，上游修复后撤除。

**定性更新：这是 `mcore_bridge` 参数转发 bug 的修复，不是 XSwift 专属能力迁移。** 它随 XSwift 退役一起处理，但不因厂商插件移除而消失——不装 XSwift 时该缺陷仍在。

**判定：当前bool契约无需搬，不是实际checkpoint校验能力。**

XSwift wrapper不调用传入的原校验；只检测Torch caller采用bool还是error-list，返回True或[]。当前Swift已自行安装True stub，当前Torch2.9仍使用bool契约。

因此它不是“补齐planner正确性”的实现。若升级至error-list契约，应优先使用对应Swift升级或最小返回类型适配；不能在当前bool契约下无条件返回[]，也不能复制恒真绕行并宣称安全。

保存成功不证明通过真实overlap/覆盖校验。完整DCP+optimizer+RNG恢复应另验，若产品需要真实分片校验，需要单独决定策略并保留证据。

证据：`xswift_ext/components/swift/megatron/dcp.py` 行 10–50，`swift/megatron/init.py` 行 78–93，torch `distributed/checkpoint/default_planner.py`。

## 8. 建议的实现职责与方式

以下是设计建议，尚未新增接口、文件或实现。

| 对应优化/功能 | 建议职责 | 不建议的方式 |
|---|---|---|
| DDP 初始化跨流同步、THD RoPE fallback 保留 CP group | Swift/mcore_bridge 外部框架适配 | 全局 patch Stream、复制整个框架函数 |
| MoE large-weight 权重转换、MoE LoRA merge/unmerge 写回 | TE 参数契约适配，覆盖所有消费者 | 分散互相覆盖的临时属性 shim |
| BSHD RoPE 融合选择 | provider 语义/native/vendor 与准确调用坐标 | 只登记符号而不验证契约 |
| Megatron 首批峰值形状 warmup、CP warmup、MoE/多模态 warmup 路由保护、HF/DeepSpeed warmup | 框架数据策略/平台 allocator 保护，opt-in | 默认强制填充、两套 collator 叠加 |
| Evaluation 厂商模式保护 | 平台策略+框架生命周期 | 跳过 evaluate、硬编码持久 env |
| Embedding object payload CPU gather | 对应 loss 分支的小 helper | 替换所有 collective 或切换通信后端 |
| Profiler 训练回调、在线 token 吞吐日志 | 官方 callback 扩展 | 改整段 trainer、保留 xswift 运行依赖 |
| Conv3d workaround、DCP stub 返回契约适配 | 版本与能力探测，优先上游 | 同版本重复 patch、无条件恒真 |

原则：

1. 默认不改变用户模型与策略；需要侵入时opt-in且状态可见。
2. 沿用手动触发+环境变量定点框架包装，不回到全局 `_call_impl` patch。
3. 非性能生命周期适配不要通过空semantic偷渡为“算子已通过门禁”。
4. 功能兼容和性能接管分开登记，分别记录来源、适用范围、版本与验证结果。
5. 不以直接import xswift组件当作“XSwift退役”。迁移后的运行依赖必须干净。
6. 所有框架外部hook要覆盖已加载/未来加载、别名、重复启停、卸载恢复、厂商写入顺序。
7. 具体挂点与最小改动在实施前确认；本文不预先虚构框架API。

### 8.1 TT底座的前置限制

之前复核已确认TT仍有下列问题，迁移新功能前不能忽略：

- detached候选可能跳过梯度门禁；
- 精度门禁以fp32为主，未全面验证生产dtype；
- 首次零输入可能误判RMSNorm变体；

- 完整启动链失败原子性未闭环。

这些不是XSwift新增功能，但直接影响新adapter的可信准入和外部hook生命周期。参考已落盘复核：

### 9.2 验证方法

1. 先将已确认的最小问题固化为回归用例，证明旧行为失败、修补后成功。
2. 每次只变一个功能点或一个配置变量，分离正确性与性能实验。
3. 对照至少包含：原XSwift目标能力开启、TT/框架替代能力开启、无包模式；固定XME及其他厂商开关，不能混合归因。
4. 初始权重、可训练参数、数据顺序、tokenization、dtype、并行配置一致。
5. 保存原始loss/grad_norm、输入指纹和实现调用证据，不只看四舍五入日志。
6. 对有非确定性路径先测同模式噪声；数值阈值按具体语义预先确认，不用“差得小”代替正确性。
7. 性能在足够长稳定训练中按窗口测量，记录startup/warmup/save开销，避免并发占卡。
8. 不适用项明确标记；未跑项目不能标记完成。

### 13.5 评估和embedding：未复现者不立即补

三组真实Qwen训练中，`qwen_eval_nofork`和`qwen_eval_guard`每组6个全局update，iteration3/6各eval一次。保护组只在evaluate期间设置`HYDRA_DISABLE_FAST_FC_MEMORY_EFFICIENT=1`，每步训练flag均恢复为原None；四rank所有记录metrics精确一致。rank0两次eval loss为1.9041519165039062、1.874502182006836；两组峰值allocated相同，分别8757.01611328125、8757.17431640625 MiB。短6步不用作吞吐或长期数值结论。

另测环境初值None/0/1 × 正常/抛异常六组合，保护期间值1、finally恢复原值全部通过。当前TE确有运行时环境读取，但不是所有优化开关组合都在本轮训练中启用；本机无保护可运行只能支持“当前配置不必马上补”，不能保证开启其他省显存fast-FC路径仍安全。

普通HF `InfonceLoss`使用真实accelerate对象gather，两rank、每rank3个8维embedding、labels`[1,0]`、开启batch negatives/hardnegative1。原设备payload与CPU保护同dtype loss和本地梯度逐位一致；FP32 rank0 loss16.923118591308594，BF16为16.875。CPU保护使远端payload先在CPU再恢复到输入设备，本地梯度仍在场。总8 rank-case无异常；不同rank payload按真实设备号反序列化的跨设备影响、吞吐/内存及其他后端未测，因此暂不补而不是删除风险项。

### 13.6 BSHD RoPE：正确性先于收益

输入shape三组`[8,1,2,64]`、`[128,2,8,64]`、`[2048,1,8,64]` × FP32/BF16 × rotary_dim32/64，共12组。同输入/角度/上游梯度比较native、TT候选、XSwift选择的XME融合、当前TT门面，并用独立CPU FP64公式辨别误差。

- 当前TT门面12组均与native前向/dgrad逐位相等；manager证据`vendor-fused:rope_bshd`被拒、`native:rope_bshd`绑定并调用，证明安全回退在场。
- rotary_dim32的厂商/TT候选出现大dgrad误差：最长组FP32最大7474.32080078125，BF16最大7484.1875；native相对FP64约4.08e-7/0.0251。候选也偏离FP64，不是简单“不同规约噪声”。
- 抽到`torch.ops.custom_ops.rotary_pos_emb_backward`，同值grad比较strided/contiguous，6组两者都错（contiguous最大约11.1651），所以**不能把加contiguous当作已确认修复**；stride不是足够解释。kernel维度/布局语义尚未根治定界。
- rotary_dim64误差较小但非逐位等价：最长FP32 dgrad最大约3.54e-4，BF16为0.03125；尚未给该族整体通过精度门禁，不称“融合已正确”。
- 诊断性独立fwd+bwd计时（5次warmup、3组×20次、同步边界）显示dim64候选/native延迟比0.44277565～0.49022996，native/candidate为2.03985902～2.25848011；由于精度未统一准入且无整网命中，**不是可用优化收益，也不加总进整网提速**。精确各shape样本和双向倍率在summary，短算子测试不能外推整网。

真实Qwen的THD调用已经取证：首批t`[191,1,4,256]`、freqs`[191,1,1,64]`、CP1，两者首维相等，确定走batched，不触发第二项fallback。调用期间BSHD符号为`xmegatron_ext.components.core.models.common.embeddings.rope_utils`函数，说明bridge生命周期暂覆盖TTdispatcher；“启动时绑定”与“真实训练期间控制权”须拆开验收。新6步证据验证当前调用，不外推前200步每次形状。

### 13.7 Profiler、在线日志、Conv3d与DCP

**Profiler：** 当前官方`megatron_callbacks_map`键为`print/default_flow/swanlab/wandb/tensorboard`，没有ProfilerCallback的等价注册；XSwift仅在`MEGATRON_PROFILE`启用后向trainer追加实例，不可直接传一个不存在的`profiler`注册key。独立实例调用真实torch.profiler，正常3步trace193 events、提前结束2步149 events，包含真实计算/梯度host事件；rank0不在[1]时不采集；on_train_end关闭torch profiler。进一步collect_memory/shapes/callstack启用，真实memory HTML和压缩trace导出成功。

但trace没有`kernel`或其他device kernel事件，不能用于kernel时间归因。NVTX正常/提前两组都在`cudaProfilerStart`报“profiler disabled while using external profiling tool”，没有进入完整窗口；不是提前清理已通过。snapshot、nsys外部采集、resume与异常窗口均未认证，不能把厂商callback直接搬过来宣称生产diagnostic全覆盖。

**在线日志：** 真实PrintCallback，clock单变量控制、resume iteration10、下一步11、GBS4/seq8192/world4；厂商字段`tokens/s/gpu=8192`、`avg_tokens/s/gpu=4096`与其名义公式相符，基础日志已有train_speed2s/it。它不知道每batch实际token数，且最近一步时长与日志窗口并不等同。新Qwen首批只有191 token/卡时，名义8192可高估约42.89倍；这只是该batch的口径对照，不是实际吞吐计时。不要复制字段名后说“真实token监控已支持”。

**Conv3d：** Swift已经安装`_original_forward`，XSwift wrapper检测后返回同一函数，重复patch无净效果。受限组合input`[1,3,4,8,8]`、weight`[8,3,2,2,2]`、stride2、padding0、dilation1、groups1；FP32 forward对FP64最大约4.82e-7，dgrad/wgrad/bgrad最大约3.67e-7/6.60e-6/6.78e-7。FP32两次随机层测试各与自己的FP64参考对账，不据其不同权重宣称两模式逐位相等。

BF16 forward可运行，wgrad/bgrad可运行，**dgrad在`aten::unfold_backward`报NOT IMPLEMENTED**。分别只求input/weight/bias梯度确认了失败阶段；直接linear、unfold forward可运行。原Swift和XSwift均失败；stride不等kernel、非零padding、dilation2、groups2都按helper约束抛NotImplementedError。该helper只能算当前版本和受限参数FP32替代，不是完整Conv3d/BF16支持。

**DCP：** 当前DefaultSavePlanner调用方期望bool，原Swift stub和XSwift wrapper都给bool。真实DCP保存/加载模型weight`[8,4]`和optimizer exp_avg`[32]`，恢复逐位一致，两模式通过。但恒真stub没有执行global shard integrity校验；本例没有TP/EP optimizer sharding、完整LoRA恢复或断点训练continuation，不宣布完整checkpoint能力已迁移。

### 13.8 基于实测的工作队列与非目标

1. **THD fallback group契约**：可复现、修复边界最小，优先推进。
2. **MoE转换 + LoRA真实存储写回**：共享TE参数契约，但验收各自独立。MoE large-weight为目标时必补；不把XME getter前置缺口混入XSwift任务。
4. **BF16视觉输入梯度**：目标需要训练该Conv3d patch embedding时先补底座算子，插件复制无效。
5. **RoPE融合**：继续native安全回退；先解决候选数值/动态接线，再谈收益，不按测速结果强开。
6. **生产profiler及真实token日志**：按诊断和可观测性需求补callback/后端，P2不阻断现有训练。
7. **DDP、eval当前模式、embedding CPU保护**：保留方法/原始数据/触发假设，当前不因清单要求就写patch。

厂商预热及配套mask已按2026-10-30决策全部退出工作队列，不做移植。上面保留原序号便于追溯。

“当前必须补齐”有前提：现有DP4 dense训练/eval已通过，没有证据说明其余缺口都阻断当前任务。退役验收针对用户约定的保留能力，不要求覆盖已放弃的全部15项历史能力。其余条件性能力及未验证组合仍需如实登记；模型效果、长程loss等价、所有并行、设备kernel profiling、完整分片恢复和无包卸载仍未认证。
