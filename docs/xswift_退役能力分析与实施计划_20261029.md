## 0. 结论与退役定义

**用户决策（2026-10-30）：XSwift 厂商预热功能全部放弃，不迁移、不补齐。** 包括厂商 Megatron/HF/DeepSpeed 首批填充、CP/SP 预热扩展、dummy token 随机化与位置整理、text/视觉 `warmup_padding_mask` 注入及其转发。相关缺口退出实施队列与退役等价验收，只保留历史分析和实测数据；“放弃”不是“已支持”。

本机 Swift 的 `SWIFT_PAD_WARMUP` 属于已存在的独立策略，本次不删除、不改变其配置，也不将其扩展列为 XSwift 退役要求。本轮仅调整迁移范围，没有修改 site-packages 或卸载插件。15 项/18 个接口仍用于历史盘点，不再作为要求全部等价迁移的覆盖率分母；一般 packed/CP、原生 router mask、视觉输入与 THD RoPE 契约仍按正常训练能力验收。

~~**当前 dense Qwen 的训练主流程可以关闭 XSwift 运行，但尚不能宣布 XSwift 全部能力已由 TT/原框架覆盖，更没有完成“卸载 XSwift 后功能无退化”的验证。**~~

> **2026-11-18 更新（以 §16 为最新口径）**：「卸载后功能无退化」的验证**已完成**。
> 在 `XTE_GROUPED_GEMM_LARGE_WEIGHT=0` + `HYDRA_DISABLE_FAST_FC_MEMORY_EFFICIENT=1`
> + `XTE_DISABLE_FAST_BF16_CACHE=1` 下，**物理移除 xswift_ext 包**后 dense 与 MoE
> 各 100 步训练：loss 逐位一致、HF 导出张量 100% 逐位一致（372/372 与 231/231）、
> 性能无方向性退化、峰值显存不变。
>
> **但三个开关缺任一都会产生静默损坏的 checkpoint**（exit=0、loss 逐位一致、零报错，
> 只有读权重数值才发现）：LW=1 → 180 个 MoE 专家权重导出为 ~3.7e33；
> mem-efficient 未关 → `lm_head` 导出为 3.7e33。详见 §16.0/§16.3。
>
> 同时推翻两条旧结论：B6「Evaluation 厂商模式保护已关闭/生产 no-op」**不成立**
> （§16.4-A）；§15.4 的「退役路径不闭合」**过于悲观**——关 LW 即可闭合，代价是
> 放弃 LW=1 的 MoE 性能收益（§16.4-B）。
>
> 功能清单侧已收口：B1/B5/B7 由 TT 承接，真正还缺的只有 Profiler callback 与真实
> token 日志两项 P2。§15 的三条机制问题（补丁共存谎报 `applied`、升级安全探测误判、
> E14 升级会撤掉 large-weight shim）仍然有效，与本轮结论不冲突。
>
> **2026-11-19 再更新（最新口径见 §17/§18）**：§15 的三条机制问题中，
> 前两条**已在 TT 包内修复**（§17），E14 那条留给升级冒烟执行。
> 更重要的是补上了一个此前未言明的前提——**§16 的三状态验证里 TT 并不在场**，
> 它证明的是"包可以移走"而非"退役后由 TT 承接"。§18 补齐了这一格：
> dense 与 MoE 各一轮 TT 全程在场的三状态 e2e，退役态下 TT 的三条功能补丁
> 全部 `applied`、无覆盖，HF 导出仍 372/372 与 231/231 逐位一致。
> **至此"XSwift 可以完全退役"是有承接证据的结论**，剩余只有 LW=1 去向这一个
> 产品决策（其真实性能代价本机测不出，见 §18.2-①）。

**文档主线：XSwift 做了哪些优化/兼容处理 → TT 流程哪些已经支持 → 哪些尚未支持 → 从尚未支持的部分按优先级逐项完善。**

以功能名称为唯一分析单位，不再使用“接口编号”和“能力编号”两套代号。一个功能可以修改多个接口；接口清单只用于追溯实现，不作为独立工作项，也不按接口数量计算覆盖率。

### 0.1 三个不同的完成层级

| 层级 | 含义 | 当前结论（2026-11-18 刷新，依据 §16） |
|---|---|---|
| 插件关闭 | `XSWIFT_PLUGIN_ENABLE=0`，不走自动初始化 | **已验证**：dense（真实 Qwen3.5-0.8B + LoRA）与 MoE（合成 BF16）各 100 步，loss 与 HF 导出逐位一致。注意生产 `run.sh` 有 `RUNTIME_SCRIPT_DIR` 覆盖坑会让该开关失效（§16.6 坑 1） |

### 0.2 本文范围

本文只评估 **XSwift** 退役。默认保留：

- Swift / Megatron Core / mcore_bridge；
- torch_xmlir 的设备对接及算子提供；
- 当前厂商 TE、HydraX、通信和 xpu_fla 基座。

## 2. 实现追溯：各优化修改了哪些接口

## 4. 必须优先补齐的正确性能力

### DDP 初始化跨流同步

**状态：缺少显式双向流依赖；本机 P800 已做专项验证，未复现数据竞争。属于跨后端兼容风险，不能表述为当前训练已发生错误。**

当前 Swift 在新 Stream 上构建 DDP，但没有与默认/当前流的双向依赖。XSwift 显式执行：

1. 新流等待当前流，确保参数初始化已经完成。
2. 在新流上构建 DDP。
3. 当前流等待新流，确保后续 broadcast/forward 不抢跑。

TT Stream 门面只转发底层能力，不会补调用顺序，因此不是等价覆盖。

**2026-10-29 本机专项实测：**

- P800 OAM 四卡，保持原训练环境开关；XSwift/XME 自动初始化关闭。xmlir 与 TT 分别在新进程验证，单项对照只调用 XSwift 的双向等待 wrapper，不开启其余插件 patch。

### THD RoPE fallback 保留 CP group

**状态：本机已稳定复现，根因确认；生产修复尚未实施。与 DDP 不同，这是当前安装栈中可直接触发的参数契约错误。**

mcore_bridge 包装器 pop 掉 `cp_group`，非 batched fallback 没有传给捕获的原函数。当前 Megatron 原 THD 函数要求 `cp_group` 非 None。

XSwift 能识别 closure 中捕获的原 THD 实现，向 fallback 保留 group；无显式 group 时从 parallel_state 获取。

#### THD 是什么，哪些输入触发错误

`THD` 表示 packed token 数 T、attention head 数 H、head dimension D；多条变长序列沿 T 拼接，`cu_seqlens` 保存各序列边界。CP group 给出当前 context-parallel 分组的 size/rank，用于选择每条序列上属于本 rank 的旋转位置。即使 CP=1，当前 Megatron 原函数也要求一个非空 group，不接受用 None 表示单卡。

当前 bridge 用 `freqs.shape[0] == (cu_seqlens // cp_size)[-1]` 判定 batched RoPE：

- 相等：频率已经覆盖本 rank 整个 packed token 流，直接转到 BSHD 计算，不调用原 THD fallback。
- 不相等：例如频率只提供“最大单条序列长度”的传统 RoPE 表，需要原 THD 按各序列及 CP rank 取位置；此分支漏传 group，确定报错。

#### 本机复现矩阵与输入

2026-10-29，保持同机 P800 环境，XSwift/XME 自动初始化关闭；xmlir、TT 分别使用 CP1 单 rank 和 CP2 两 rank 的真实进程组，在四个独立 torchrun 启动中验证。TT 显式激活且 `TT_RESTORE_VENDOR=perf`；没有开启全套 XSwift 插件。对照仅在独立测试进程内将私有 THD 函数临时换为 XSwift 的 THD-only wrapper，每个 case 后恢复。

这些 FP64 差值是此输入下的低精度计算观测，不是本次 group 修补产生的额外误差；修补对照与原 Megatron 同 dtype 实现逐位相等。未基于 FP64 数值放宽或制定通用模型精度阈值。

#### 根因证据链与假设记录

公共入口的完整调用堆栈：测试 `rope_utils.apply_rotary_pos_emb` → `mcore_bridge/patcher.py:232` → Megatron 公共入口 `rope_utils.py:308` → bridge 私有包装 `patcher.py:211` → 原 THD `rope_utils.py:201` 抛 ValueError。原始完整堆栈在每 rank JSON 的 `traceback` 字段。

| 假设 | 实测结果 | 判断 |
|---|---|---|
| 调用者没传 group | 显式传真实 group 仍报错；公共入口默认 group 也报错 | 排除为必要原因 |
| 只有 CP>1 会失败 | CP1/CP2 non-batched 都100%失败 | 排除；CP1同样受影响 |
| dtype 或设备 kernel 不兼容 | FP32/BF16同样在参数检查处失败；正确 group 下前反向通过 | 本用例排除 |
| bridge 消耗 group 后未转发 | 原函数 profile 记录 group=None；单项保护后为同一个真实 group | 已确认根因 |
| TT 已通过 BSHD provider 修补 THD | TT 组同样报错；其登记对象是 BSHD，不是 fallback 参数契约 | 排除 |

#### 为什么之前 Qwen 四卡能运行

之前实际保存的 TT 训练 `args.json` 已核对：`padding_free=True`、`context_parallel_size=1`、`apply_rope_fusion=False`，不是“默认 fused THD 绕开错误”。Qwen3.5 MRoPE 按输入 position IDs 生成整段频率，若频率长度等于 packed 本地总长，就进入已验证正常的 batched 分支，因此非 batched 缺口不会触发。

这是由实际配置和源码条件支持的解释；之前训练没有逐次记录 THD 频率形状，本轮也未重跑 Qwen，所以不宣称已证明每次历史调用的分支。还确认 bridge TransformerLayer 在 unfused attention 期间会临时覆盖 BSHD 符号，TT 的 BSHD 绑定成功不能当作该次调用命中的证据；该行为作为其他性能项线索记录，不在本轮顺手修改。

#### 修复位置归属分析（2026-10-30，用户已确认）

**结论：根治应改 `mcore_bridge/patcher.py` 的 `_patch_mrope()`，不在 Swift 训练对接层，也不改 Megatron 本体。** 这是 bridge 自身的参数转发缺陷，不是 XSwift 独有能力。

| 层级 | 位置 | 当前行为 | 是否本次错误来源 |
|---|---|---|---|
| Swift 训练对接 | `swift/megatron/trainers/*` | 组织训练流程与模型调用，不直接构造 THD 的 `cp_group` | 否：无证据表明它漏传 |
| Megatron 公共入口 | `rope_utils.apply_rotary_pos_emb:250-266,308-311` | `cp_group is None` 时取当前 CP group 再传给私有 THD | 否：行为正确 |
| **bridge THD 包装** | `mcore_bridge/patcher.py:200-213` | `pop('cp_group')` 后用于算 `cp_size`，fallback 调原函数时未传回 | **是：根因所在** |
| Megatron 原 THD | `rope_utils._apply_rotary_pos_emb_thd:178-204` | 需要 group 取 size/rank；为 None 时显式报错 | 否：报错是在暴露上层缺陷 |

**`pop()` 本身有其目的，不能简单改成 `get()`。** batched 分支转调的 `_apply_rotary_pos_emb_bshd`（`rope_utils.py:92-98`）签名没有 `cp_group`，保留该键会触发 unexpected keyword。真正的缺陷是两条分支共用同一份被删键的 `kwargs`，fallback 未按原函数契约补回。“`pop` 是为 BSHD 服务”由函数签名推断，未查提交历史确认作者意图。

| 候选修复位置 | 评价 |
|---|---|
| **`mcore_bridge/patcher.py`** | **首选**：在参数丢失发生处修正，两条分支契约集中维护，不新增依赖 |
| Swift/XSwift 外层 wrapper（现状） | 仅受限兼容：重复分支判断、依赖 `inspect.getclosurevars` 查闭包、受导入与绑定顺序影响；闭包查找失败时退回原 bridge，**不保证修掉该错误** |
| Megatron 原 THD 自动兜底 | 不合适：把 `None` 兜成全局 group 会掩盖 bridge 丢弃调用者显式 group 的问题，兜到的 group 也不一定是调用者原本指定的那个 |

关键原则：**不能用“重新获取一个默认 group”代替“保留调用者明确指定的 group”**，否则报错消失但分组语义仍可能错。

bridge 内最小修法：显式传入的 group 用于算 `cp_size`，fallback 时把**同一个对象**传给原 THD；batched 分支继续不传该键；需要 fallback 且 group 缺省时再解析真实 CP group，不给原本可用的 batched 分支增加新前置要求。不需要取消 `pop()`、不改 batched 判定条件、不重写 RoPE 计算。

交付方式与逻辑归属分开：能维护或向上游提交 `mcore_bridge` 时直接修源头并走受控版本发布，不以手改 `site-packages` 为最终交付；暂时不能改依赖时，TT 可提供针对受影响版本的 bridge 兼容修补，但须标注临时兼容、不放进性能 provider、不依赖 `xswift_ext`，上游修复后撤除。

**定性更新：这是 `mcore_bridge` 参数转发 bug 的修复，不是 XSwift 专属能力迁移。** 它随 XSwift 退役一起处理，但不因厂商插件移除而消失——不装 XSwift 时该缺陷仍在。

### BSHD RoPE 融合选择

**状态：TT门面安全回退验证通过；融合候选部分旋转backward大误差已复现，contiguous未解决；真实Qwen期间BSHD被暂绑定厂商函数。先保精度再接线，详见 §13.6。**

XSwift的BSHD wrapper直接import XME组件函数并返回它。即使XME自动插件关闭，只要包在场，XSwift仍可直接使用该实现。因此既有“XME_PLUGIN_ENABLE=0”不能代表没有XME组件依赖。

TT已有rope_bshd provider和Megatron坐标，但四卡证据未命中该provider；packed/THD/模型专用路径及原函数closure、导入别名、后续patch写入，都会影响实际调用点。

还需要确认输入角度/cos-sin、布局、CP group、部分旋转、返回结构、dtype以及要求的梯度契约。不要只补坐标就宣称覆盖。

**验收：**以真实forward和provenance证明实际选中实现、调用计数与回退；用前反向/生产dtype/小大shape门禁确认语义与收益。若当前模型无需该融合，可记录为该模型不适用，但不能算全特性迁移完成。

证据：`xswift_ext/components/mcore_bridge/patcher.py` 行 75–85，TT `ttorch/provider/bind_targets.py` 与 `impls/rope_bshd/`。

## 6. 观测与易用性能力

### Profiler 训练回调

**状态：需要独立生产接入；厂商真实host trace/rank/提前结束/memory timeline部分通过，但device kernel事件未采到、NVTX启动失败，不能原样复制后宣称完整。详见 §13.7。**

XSwift在trainer初始化结束后，仅当 `MEGATRON_PROFILE` 开启时追加callback。callback内部的args兜底不意味着单独传CLI profile参数就会触发该注入。

原能力包括：

- profile step窗口与rank筛选；
- torch.profiler trace及shape/callstack；
- memory history/snapshot/timeline；
- 可选Chakra；
- cudart/NVTX分支。

**建议：**用Swift官方callback注册/选择机制接入，而不是复制整段trainer或依赖xswift包。现有TT测试EvidenceCallback可借鉴生命周期，不可当作功能已交付。

不要原样搬入已知边界：原callback在rank筛选前可能开启memory history；提前结束时的nsys/NVTX清理并未与PyTorch profiler同等闭环。XPU trace、snapshot、timeline、NVTX也应分别验证，API存在不代表设备支持。

**验收：**窗口/rank准确，异常/提前结束/resume清理，无训练长期额外开销，输出文件可解析，内存历史正确关闭；不适用功能明确提示。

证据：`xswift_ext/components/swift/megatron/trainers/base.py` 行 72–250，TT `tests/e2e/compare_qwen_four_rank.py`。

### 在线 token 吞吐日志

**状态：基础日志已有，XSwift新增字段未在TT生产路径等价补齐。**

Swift已有memory、elapsed、remaining、train_speed。XSwift主要增加 `tokens/s/gpu`、`avg_tokens/s/gpu`。

原实现按 `GBS * seq_length` 估算token，除以完整world_size；计时不显式同步，瞬时值来自最后一步。变长/packed或模型并行下不能直接等同真实有效token吞吐。

**建议：**保留用户可见指标，但明确input tokens、有效label tokens、全局/每设备、DP/模型并行去重、日志窗口与warmup口径。精确同步测量采用显式诊断模式，避免默认每步同步破坏overlap。

四卡离线汇总已按实际tokens与各rank最大同步耗时统计，但它是测试工具，不是在线PrintCallback。

**验收：**手工token计数对账、gradient accumulation、变长padding_free、TP/PP不重复计数、resume累计区间、日志字段向后兼容。

证据：`xswift_ext/components/swift/megatron/callbacks/print.py` 行 29–73，`swift/megatron/callbacks/print.py`，TT `tests/e2e/summarize_qwen_four_rank.py`。

## 7. 当前无需搬运的能力

### Conv3d workaround

**判定：当前框架已提供同helper，受限参数FP32前反向通过；BF16输入梯度在unfold_backward失败，原厂商wrapper也不能解决。helper不要重复复制，dtype底座缺口另处理，详见 §13.7。**

Swift在torch版本 `2.9.0 <= version < 2.10.0` 时自动安装 `_patch_conv3d()`；XSwift只无条件调用同一个helper，没有独立kernel。

现有patch仅支持stride=kernel_size、padding=0、dilation=1、groups=1，不是通用Conv3d能力。未来升级torch仍需复核是否存在该兼容需求，不能无限期强制套用。

**验收：**去掉xswift后对应patch仍安装、目标视频patch-embedding前反向正确；不支持参数明确报告。此项不要求重写通用Conv3d。

证据：`swift/model/utils.py` 行 261–286，`xswift_ext/components/swift/model/conv3d.py` 行 24–33。

### DCP stub 返回契约适配

**判定：当前bool契约无需搬，不是实际checkpoint校验能力。**

XSwift wrapper不调用传入的原校验；只检测Torch caller采用bool还是error-list，返回True或[]。当前Swift已自行安装True stub，当前Torch2.9仍使用bool契约。

因此它不是“补齐planner正确性”的实现。若升级至error-list契约，应优先使用对应Swift升级或最小返回类型适配；不能在当前bool契约下无条件返回[]，也不能复制恒真绕行并宣称安全。

保存成功不证明通过真实overlap/覆盖校验。完整DCP+optimizer+RNG恢复应另验，若产品需要真实分片校验，需要单独决定策略并保留证据。

证据：`xswift_ext/components/swift/megatron/dcp.py` 行 10–50，`swift/megatron/init.py` 行 78–93，torch `distributed/checkpoint/default_planner.py`。

## 8. 建议的实现职责与方式

以下是设计建议，尚未新增接口、文件或实现。

| 对应优化/功能 | 建议职责 | 不建议的方式 |
|---|---|---|
| DDP 初始化跨流同步、THD RoPE fallback 保留 CP group | Swift/mcore_bridge 外部框架适配 | 全局 patch Stream、复制整个框架函数 |
| MoE large-weight 权重转换、MoE LoRA merge/unmerge 写回 | TE 参数契约适配，覆盖所有消费者 | 分散互相覆盖的临时属性 shim |
| BSHD RoPE 融合选择 | provider 语义/native/vendor 与准确调用坐标 | 只登记符号而不验证契约 |
| Megatron 首批峰值形状 warmup、CP warmup、MoE/多模态 warmup 路由保护、HF/DeepSpeed warmup | 框架数据策略/平台 allocator 保护，opt-in | 默认强制填充、两套 collator 叠加 |
| Evaluation 厂商模式保护 | 平台策略+框架生命周期 | 跳过 evaluate、硬编码持久 env |
| Embedding object payload CPU gather | 对应 loss 分支的小 helper | 替换所有 collective 或切换通信后端 |
| Profiler 训练回调、在线 token 吞吐日志 | 官方 callback 扩展 | 改整段 trainer、保留 xswift 运行依赖 |
| Conv3d workaround、DCP stub 返回契约适配 | 版本与能力探测，优先上游 | 同版本重复 patch、无条件恒真 |

原则：

1. 默认不改变用户模型与策略；需要侵入时opt-in且状态可见。
2. 沿用手动触发+环境变量定点框架包装，不回到全局 `_call_impl` patch。
3. 非性能生命周期适配不要通过空semantic偷渡为“算子已通过门禁”。
4. 功能兼容和性能接管分开登记，分别记录来源、适用范围、版本与验证结果。
5. 不以直接import xswift组件当作“XSwift退役”。迁移后的运行依赖必须干净。
6. 所有框架外部hook要覆盖已加载/未来加载、别名、重复启停、卸载恢复、厂商写入顺序。
7. 具体挂点与最小改动在实施前确认；本文不预先虚构框架API。

### 8.1 TT底座的前置限制

之前复核已确认TT仍有下列问题，迁移新功能前不能忽略：

- detached候选可能跳过梯度门禁；
- 精度门禁以fp32为主，未全面验证生产dtype；
- 首次零输入可能误判RMSNorm变体；
- FX算子名称序列不是完整SSA等价；
- 别名漏扫、卸载消费者残留、重复绑定、状态报告问题；
- 完整启动链失败原子性未闭环。

这些不是XSwift新增功能，但直接影响新adapter的可信准入和外部hook生命周期。参考已落盘复核：

`transformers_symbrewrite_插件_TT覆盖能力复核_20261028.md`

### 9.2 验证方法

1. 先将已确认的最小问题固化为回归用例，证明旧行为失败、修补后成功。
2. 每次只变一个功能点或一个配置变量，分离正确性与性能实验。
3. 对照至少包含：原XSwift目标能力开启、TT/框架替代能力开启、无包模式；固定XME及其他厂商开关，不能混合归因。
4. 初始权重、可训练参数、数据顺序、tokenization、dtype、并行配置一致。
5. 保存原始loss/grad_norm、输入指纹和实现调用证据，不只看四舍五入日志。
6. 对有非确定性路径先测同模式噪声；数值阈值按具体语义预先确认，不用“差得小”代替正确性。
7. 性能在足够长稳定训练中按窗口测量，记录startup/warmup/save开销，避免并发占卡。
8. 不适用项明确标记；未跑项目不能标记完成。

当前静态搜索未发现TT生产源码、安装Swift/mcore_bridge/XME源码对 `xswift_ext` 的直接引用；这是有限范围静态证据，不是完整无包验证。

- **扫 `/klx_dummy_lib` 痕迹**：XSwift `import_module_safe` 在 import 失败时注入
  指向该路径的空模块，会掩盖真实 import 失败并污染无包验证的 `sys.modules` 审计。
  检查方式 `ttorch.bridge.vendor_retire.dummy_module_traces()`，期望空列表。
- **核对三个导出安全开关**：`XTE_GROUPED_GEMM_LARGE_WEIGHT=0` /
  `HYDRA_DISABLE_FAST_FC_MEMORY_EFFICIENT=1` / `XTE_DISABLE_FAST_BF16_CACHE=1`
  （§16.3 的静默损坏来源）。检查方式 `vendor_retire.export_safety_issues()`，
  期望空列表；big_leaf 生产入口已内置 fail-fast。
- **复核 TT 功能补丁是否被厂商插件顶掉**：`framework_patch.patch_status()` 的
  运行期复核；过渡期（两套同开）必须在**框架 import 之后**再看一眼，
  安装期的结论不作数。

**最终退役标准：不是删掉XSwift名字，而是约定场景中不再依赖它的任何运行代码，兼容、数值、性能和观测能力有可重复证据。**

### 13.5 评估和embedding：未复现者不立即补

另测环境初值None/0/1 × 正常/抛异常六组合，保护期间值1、finally恢复原值全部通过。当前TE确有运行时环境读取，但不是所有优化开关组合都在本轮训练中启用；本机无保护可运行只能支持“当前配置不必马上补”，不能保证开启其他省显存fast-FC路径仍安全。

**2026-11-05 终验（厂商语义 + 直接复测，关闭上述保留口径）**：厂商确认 fast FC mem-efficient=权重转置训练 inplace；在 hydrax linear 本体（XME linear 调用方式逐字复制，8192×4096 bf16/fp32）上 `HYDRA_DISABLE_FAST_FC_MEMORY_EFFICIENT` 开/关两态数值逐位一致、权重无改写、train→eval→train 一致，ON 省峰值显存 224/448 MiB、速度 ~1.00x；且生产路径（两插件均关）linear 不经 hydrax fc_fusion，该 env 无作用对象。详见 `experiments/b6_fast_fc_mem_efficient/RESULTS.md`。"其他 fast-FC 路径仍安全"的保留不再成立——生产路径根本没有其他 fast-FC 消费者。

普通HF `InfonceLoss`使用真实accelerate对象gather，两rank、每rank3个8维embedding、labels`[1,0]`、开启batch negatives/hardnegative1。原设备payload与CPU保护同dtype loss和本地梯度逐位一致；FP32 rank0 loss16.923118591308594，BF16为16.875。CPU保护使远端payload先在CPU再恢复到输入设备，本地梯度仍在场。总8 rank-case无异常；不同rank payload按真实设备号反序列化的跨设备影响、吞吐/内存及其他后端未测，因此暂不补而不是删除风险项。

### 13.6 BSHD RoPE：正确性先于收益

输入shape三组`[8,1,2,64]`、`[128,2,8,64]`、`[2048,1,8,64]` × FP32/BF16 × rotary_dim32/64，共12组。同输入/角度/上游梯度比较native、TT候选、XSwift选择的XME融合、当前TT门面，并用独立CPU FP64公式辨别误差。

- 当前TT门面12组均与native前向/dgrad逐位相等；manager证据`vendor-fused:rope_bshd`被拒、`native:rope_bshd`绑定并调用，证明安全回退在场。
- rotary_dim32的厂商/TT候选出现大dgrad误差：最长组FP32最大7474.32080078125，BF16最大7484.1875；native相对FP64约4.08e-7/0.0251。候选也偏离FP64，不是简单“不同规约噪声”。
- 抽到`torch.ops.custom_ops.rotary_pos_emb_backward`，同值grad比较strided/contiguous，6组两者都错（contiguous最大约11.1651），所以**不能把加contiguous当作已确认修复**；stride不是足够解释。kernel维度/布局语义尚未根治定界。
- rotary_dim64误差较小但非逐位等价：最长FP32 dgrad最大约3.54e-4，BF16为0.03125；尚未给该族整体通过精度门禁，不称“融合已正确”。
- 诊断性独立fwd+bwd计时（5次warmup、3组×20次、同步边界）显示dim64候选/native延迟比0.44277565～0.49022996，native/candidate为2.03985902～2.25848011；由于精度未统一准入且无整网命中，**不是可用优化收益，也不加总进整网提速**。精确各shape样本和双向倍率在summary，短算子测试不能外推整网。

真实Qwen的THD调用已经取证：首批t`[191,1,4,256]`、freqs`[191,1,1,64]`、CP1，两者首维相等，确定走batched，不触发第二项fallback。调用期间BSHD符号为`xmegatron_ext.components.core.models.common.embeddings.rope_utils`函数，说明bridge生命周期暂覆盖TTdispatcher；“启动时绑定”与“真实训练期间控制权”须拆开验收。新6步证据验证当前调用，不外推前200步每次形状。

### 13.7 Profiler、在线日志、Conv3d与DCP

**Profiler：** 当前官方`megatron_callbacks_map`键为`print/default_flow/swanlab/wandb/tensorboard`，没有ProfilerCallback的等价注册；XSwift仅在`MEGATRON_PROFILE`启用后向trainer追加实例，不可直接传一个不存在的`profiler`注册key。独立实例调用真实torch.profiler，正常3步trace193 events、提前结束2步149 events，包含真实计算/梯度host事件；rank0不在[1]时不采集；on_train_end关闭torch profiler。进一步collect_memory/shapes/callstack启用，真实memory HTML和压缩trace导出成功。

但trace没有`kernel`或其他device kernel事件，不能用于kernel时间归因。NVTX正常/提前两组都在`cudaProfilerStart`报“profiler disabled while using external profiling tool”，没有进入完整窗口；不是提前清理已通过。snapshot、nsys外部采集、resume与异常窗口均未认证，不能把厂商callback直接搬过来宣称生产diagnostic全覆盖。

**在线日志：** 真实PrintCallback，clock单变量控制、resume iteration10、下一步11、GBS4/seq8192/world4；厂商字段`tokens/s/gpu=8192`、`avg_tokens/s/gpu=4096`与其名义公式相符，基础日志已有train_speed2s/it。它不知道每batch实际token数，且最近一步时长与日志窗口并不等同。新Qwen首批只有191 token/卡时，名义8192可高估约42.89倍；这只是该batch的口径对照，不是实际吞吐计时。不要复制字段名后说“真实token监控已支持”。

**Conv3d：** Swift已经安装`_original_forward`，XSwift wrapper检测后返回同一函数，重复patch无净效果。受限组合input`[1,3,4,8,8]`、weight`[8,3,2,2,2]`、stride2、padding0、dilation1、groups1；FP32 forward对FP64最大约4.82e-7，dgrad/wgrad/bgrad最大约3.67e-7/6.60e-6/6.78e-7。FP32两次随机层测试各与自己的FP64参考对账，不据其不同权重宣称两模式逐位相等。

BF16 forward可运行，wgrad/bgrad可运行，**dgrad在`aten::unfold_backward`报NOT IMPLEMENTED**。分别只求input/weight/bias梯度确认了失败阶段；直接linear、unfold forward可运行。原Swift和XSwift均失败；stride不等kernel、非零padding、dilation2、groups2都按helper约束抛NotImplementedError。该helper只能算当前版本和受限参数FP32替代，不是完整Conv3d/BF16支持。

**DCP：** 当前DefaultSavePlanner调用方期望bool，原Swift stub和XSwift wrapper都给bool。真实DCP保存/加载模型weight`[8,4]`和optimizer exp_avg`[32]`，恢复逐位一致，两模式通过。但恒真stub没有执行global shard integrity校验；本例没有TP/EP optimizer sharding、完整LoRA恢复或断点训练continuation，不宣布完整checkpoint能力已迁移。

## 14. large weight 特性全链路分析

本章已抽离为独立文档：**`klx_large_weight_特性全链路分析_20261030.md`**（同目录）。

该文档完整收录：特性定位与上游等价物、L0–L8 修改点清单、逐层逻辑与合理性、
精度正确性的保证机制、性能收益来源（`noop_cat` 退化链）、三个追问的实证结论、
问题分级、TE 2.14 升级可行性评估、对 XSwift 退役的结论、ckpt 补丁归因与 swift 路径缺口。

一句话结论：large weight 是 **KL3 专属性能特性**，本质是"list kernel 精度 bug 被互斥禁用、
唯一可用 kernel 只吃连续 3D 张量"现状下的结构解；XSwift 在其中只提供 L7/L8 两个
mcore_bridge 契约 shim，且与 THD 同属 bridge 本体缺陷。

## 15. 退役缺口复盘：还差什么（2026-11-18）

### 15.0 结论先行

本轮不重跑 §13 的 15 项矩阵，只回答一个问题：**以今天的代码与生产配置为准，
XSwift 退役还差哪些功能点。** 结论：

1. **逐符号看，功能清单已基本收口**（18 个符号中 3 个由 TT 承接、3 个已关闭、
   4 个已放弃、3 个 LW=1 专属、2 个 P2 观测项、3 个由框架/版本替代）——真正缺的
   功能实现只剩 **Profiler callback 与真实 token 吞吐日志两项 P2**，加一个
   条件性底座项（BF16 Conv3d dgrad，生产 `freeze_vit=true` 下不触发）。
2. **但退役的真正阻塞不在功能清单上，而在三条此前未登记的机制问题**（§15.3）：
   TT 与 XSwift 的补丁共存无契约且**状态会谎报 applied**、XSwift 的版本门闸会让
   shim 整组静默退场、生产前提已从「两插件均关」反转为「两插件全开 + LW=1」。
3. **退役路径存在硬互锁**（§15.4）：生产现用 LW=1 → XSwift 的 large-weight shim
   是承重件 → 要退役必须先关 LW → 但 `TT_BIG_LEAF=1` 与 LW=1 实测硬互斥，
   且 big_leaf 在生产默认的 LoRA 形态下不绑定（零收益）。**这条链目前没有闭合解。**

本轮只做只读探测与实测，未修改 TT 源码、未改生产脚本、未卸载任何插件。
脚本与证据：`experiments/xswift_retire_gap/`（研究用，不随功能 PR 合入）。

### 15.3 新发现的三类机制缺口（本轮实测，文档此前未登记）

#### A. TT 与 XSwift 的补丁共存无契约，且 TT 的状态报告会谎报

> **已修（2026-11-19，见 §17）**：`patch_status()` 已加运行期复核（与
> `_rebind.snapshot()` 同源对账），升级安全探测已先判厂商在场。本节保留原始
> 实测记录作为归因依据，表格里的「旧行为」列即修复前形态。

三个符号（#1 #2 #3）TT 与 XSwift 同时在补，但两边都不认识对方：XSwift 走
`KlxSymbolRewriter.replace()`（`is_wrapper=False` 时是**整函数替换**），TT 走
`framework_patch` 的 `rebind`。退役过渡期两者必然同时在场（生产 XSwift=1，
而 big_leaf 必须 TT 激活）。实测两种顺序：

| 顺序 | `wrap_model` 最终实现 | `gather_object` 最终实现 | TT `patch_status()` | `assert_bindings_intact()` |
|---|---|---|---|---|
| `xswift_first`（先 import swift → 后 `activate()`） | XSwift 的 | XSwift 的，**外面套一层 TT** | wrap_model=`skipped(前置条件不满足)`、其余 `applied` | tampered=**0** |
| `tt_first`（`activate()` → 后 import swift） | **XSwift 的（TT 补丁被整体覆盖）** | **XSwift 的（TT 补丁被整体覆盖）** | 三项全 **`applied`（谎报）** | tampered=**4** |

两个具体问题：

1. **`tt_first` 下 TT 的补丁被静默摧毁，而 `patch_status()` 仍报 `applied`。**
   这正是**生产的真实顺序**——`ttorch/bridge/big_leaf/swift.py:main()` 先
   `ttorch.activate()`，再 `from swift.cli._megatron.main import cli_main`，
   swift 的 import 才触发 XSwift 的 lazy hook。更糟的是 `swift.py:100-104` 的
   「逐点检查 `applied`，禁止 pending 静默通过」这道 fail-fast **拦不住它**：
   检查发生在覆盖之前。唯一察觉的是 `assert_bindings_intact()`（tampered=4），
   但它只返回计数、**不 raise**，也没有和 `patch_status()` 对账。
2. **`xswift_first` 下 TT 把「厂商插件在场」误判为「社区已修复」。**
   TT 的升级安全探测用源码 needle `ddp_stream`（`patches.py:_ddp_fence_applies`），
   而 XSwift 的替换实现是 swift ≥4.3.2 的逐字拷贝，变量名恰好就叫 `ddp_stream`
   （`xswift_ext/.../megatron_lm_utils.py:77`）。于是 TT 判定「已修复 → 不接管」
   并如此留痕。本例净效果无害（XSwift 确实提供了栅栏），但**归因错误**：
   provenance 会把「依赖厂商插件」记成「上游已修复」，正好是退役期最不该搞错的一件事。

**缺口定性**：这不是某个功能缺失，而是**退役过渡期的补丁所有权与状态可信度缺口**。
最小修补方向（未实施）：① `patch_status()` 增加运行期复核（与绑定快照对账，
发现被覆盖要改状态并留痕，而不是停留在安装时结论）；② 升级安全探测区分
「上游修复」与「第三方 patch 在场」（例如先看 `fn.__module__` 是否来自
`xswift_ext`/`xmegatron_ext`，再看源码 needle）；③ 明确声明过渡期的推荐组合
（见 §15.5），不把「两套都开」留给用户试。

#### B. XSwift 的版本门闸会让 shim 整组静默退场

`xswift_ext/entry.py` 的门闸是**精确系列匹配**：`swift` 必须 4.3.x
（`is_supported_swift_version`，`release[:2] == (4, 3)`）、`mcore_bridge` 必须 1.5.x
（`is_supported_mcore_bridge_version`，`release[:2] == (1, 5)`）；不匹配则
`_warn_skip_once()` 发一条 warning 后**跳过整组重写**。

后果与已有计划直接冲突：**E14 规划的「mcore-bridge 升级到 ≥1.6.0 以吃到社区 THD
修复」会让 XSwift 的全部 mcore_bridge 重写一次性失效**——包括 #10–#12 的
large-weight shim。在生产仍是 LW=1 的情况下，这意味着升级当天 MoE 的权重转换与
LoRA merge 就会 `AttributeError`，而唯一提示是一条 skip warning。

**行动项**：E14 的升级冒烟必须把「LW=1 + MoE 转换 + LoRA merge」列为必测项，
否则这次升级会把一个本来被 shim 兜住的缺口变成线上故障。

#### C. 两处未登记的机制副作用

> **已补（2026-11-19，见 §17）**：① `/klx_dummy_lib` 痕迹扫描已成为包内能力
> （`ttorch.bridge.vendor_retire.dummy_module_traces()`）并接入退役检查；
> ② 「`__import__` 劫持 × meta-path finder」时序已入单测
> （`tests/unit/test_framework_patch_hook.py`）。

1. **`import_module_safe` 会注入假模块**：`xswift_ext/symbol_rewriter.py` 在目标
   import 失败时，用 `SourceFileLoader(current_path, "/klx_dummy_lib/...")` 造一个
   空模块塞进 `sys.modules`，并挂到父模块属性上。这会在进程里留下**指向不存在
   路径的模块对象**，掩盖真实 import 失败，也让「无包验证」时的 `sys.modules`
   审计失真。退役检查（§10）应显式扫 `/klx_dummy_lib` 痕迹。
2. **auto-init 用的是 `builtins.__import__` 劫持，不是 meta-path finder**：
   `xswift_ext/auto_init.py` 同时替换 `builtins.__import__` 与
   `importlib.import_module`，目标包 `("swift", "mcore_bridge")`。TT 走的是
   meta-path finder 两条通道（已出过 `_PatchFinder`/`_PostImportFinder` 互委托
   递归的真机 `RecursionError`）。**两种机制叠放的时序此前零覆盖**——A 组
   A6（绑定生命周期）的测试矩阵应补一格「`__import__` 劫持 × meta-path finder」。

### 15.4 退役路径的硬互锁：LW=1 ↔ big_leaf ↔ LoRA

把 §15.1 和 big_leaf 的能力边界放在一起，退役 large-weight shim 这条路目前**不闭合**：

```text
生产现状：LW=1（env.sh:31）+ XSwift=1
  └─ XSwift 的 #10–#12 shim 承重（MoE 转换 / LoRA merge）
     └─ 要退役 XSwift，必须先让 LW=1 不再需要 → 即关掉 LW
        ├─ 关 LW 的性能替代 = big_leaf
        │   ├─ 实测：TT_BIG_LEAF=1 与 LW=1 硬互斥（见下）→ 本来就不能共存
        │   └─ 实测：LoRA（整模块冻结）形态下 big_leaf 绑定数=0，零收益
        │           （big_leaf 文档 §12.6）
        └─ 而生产默认微调方式就是 LoRA（train_megatron.sh:62）
           → 关 LW 后 LoRA MoE 失去 LW=1 的收益，big_leaf 补不上
```

`TT_BIG_LEAF=1` 与生产 `env.sh` 的 LW=1 互斥，已实测确认（LW=1 建模后
`weight0` 不存在、`large_weight_switch=True`）：

| 入口 | 行为 |
|---|---|
| `BigLeafMegatronPlan.prepare()` | `ValueError: big_leaf DDP prepare 需要原生 LW=0 模型，不能接 LW=1` |
| `apply_big_leaf()` | `ValueError: 模型已被 apply_big_leaf 处理过或处于 LW=1` |

即：**按当前 `env.sh` 直接 `TT_BIG_LEAF=1 bash run.sh` 必然 fail-fast**，
必须同时把 `XTE_GROUPED_GEMM_LARGE_WEIGHT` 置 0（big_leaf 的 e2e 验收器正是
这么做的：`_base_env` 里硬编码 `XTE_GROUPED_GEMM_LARGE_WEIGHT=0`）。这是正确的
fail-fast，不是 bug，但它意味着**「开 big_leaf」和「保持现有 LW=1 生产配置」
是互斥的两条路**，需要产品决策而不是技术补齐。

三个候选解（均需决策，本文不预选）：

| 方案 | 代价 | 适用前提 |
|---|---|---|
| A. 生产切 full-tuning 后关 LW、上 big_leaf | 改变微调方式，非技术决策 | 业务允许 full tuning |
| B. 保留 LW=1，承接 #10–#12 shim（推翻「不迁入 TT」决策） | TT 要替厂商维护 3D↔per-expert 映射，还要吃 C1（optimizer `param_state` 裸索引重排） | 判定 LW=1 会长期留在生产 |
| C. 补齐 big_leaf 的冻结/LoRA 形态绑定（big_leaf §12.6 可选项 B/C） | 新设计：冻结参数不在 DDP buffer 内，需独立 buf 绑定路径 | 愿意为 LoRA 形态投入 |

**在这条链闭合之前，「XSwift 完全退役」不具备可执行路径**——这是本轮最重要的结论，
也是它与 §12「下一步」的差别：§12 当时认为只剩 P0 小步修补。

## 16. 完整退役验证：功能 + 精度 + 性能（2026-11-18）

### 16.0 结论先行

> **前提声明（2026-11-19 补）**：本节的全部运行里 **TT 并不在场**
> （`TT_PLUGIN_ENABLE` 未设，TT 也未安装 `.pth`）。所以本节证明的是
> **"xswift_ext 这个包可以从厂商栈里移走，厂商栈自身仍自洽"**，
> 而不是"退役后缺口由 TT 承接"。后者见 **§18**。

**XSwift 可以完全退役（包从环境中物理移除），但必须同时固定两个环境开关。**
在正确配置下，物理移除 XSwift 包后：训练 100 步 loss **逐位一致**（0 个非零差分）、
HF 导出张量 **100% 逐位一致**（dense 372/372、MoE 231/231）、性能在噪声带内
（±4%，无方向性退化）。

**必须同时满足的两个条件**（缺任一都会产生 checkpoint 静默损坏）：

| 条件 | 缺失后果（实测） |
|---|---|
| `XTE_GROUPED_GEMM_LARGE_WEIGHT=0` | MoE **180 个专家权重张量**导出为 ~3.7e33 垃圾值（4 层×16 专家×3），退出码仍为 0 |
| `HYDRA_DISABLE_FAST_FC_MEMORY_EFFICIENT=1` | `lm_head.weight` 导出为 3.7e33 垃圾值 |

两处都是**静默损坏**：exit=0、训练 loss 全程有限且与基线逐位一致、无任何
报错/告警。只有读 checkpoint 数值才能发现。**这是本轮最重要的发现**——它把
§15.4 的「退役路径不闭合」改写为「路径闭合，但有两个必须一起改的前置项」。

本轮同时推翻两条既有结论（§16.4）：B6「Evaluation 厂商模式保护已关闭、生产
no-op」不成立；§15.4「LW=1 的 shim 承重导致无解」过于悲观——关 LW 即可，
代价是放弃 LW=1 的 MoE 性能收益。

### 16.1 验证方法与口径

脚本 `experiments/xswift_retire_gap/validate_retirement.py`，复用**生产 run.sh /
train_megatron.sh 的参数化副本**（`.benchmarks/xswift_retire_20261118/script/`），
三个状态同模型、同数据、同 `seed=42`、同并行、同步数：

| 状态 | 含义 |
|---|---|
| `plugin_on` | `XSWIFT_PLUGIN_ENABLE=1` —— 生产当前配置，作为基线 |
| `plugin_off` | `XSWIFT_PLUGIN_ENABLE=0` —— 插件关闭，包仍在环境里 |
| `pkg_removed` | 物理 rename 移走 `xswift_ext/` 与 `xswift_ext_auto_init.pth` —— 真·退役 |

口径要点：

- **精度先看符号分布再看幅度**：loss 差分统计正/零/负个数，同号=系统性 bias、
  零均值=规约噪声；并额外做 **HF 导出张量逐位比对**（sha256），因为 loss 只有
  8 位小数的打印地板，比不出 1e33 这种导出期污染；
- **性能用边际 s/it**，由 swift 的累计平均 `train_speed(s/it)` 反解
  （`marginal[n] = n·avg[n] − (n−1)·avg[n−1]`），去 10 步 warmup 后取中位数；
  不用累计平均（首步编译会被摊薄）；
- **包移除可逆**：rename 而非 delete，`finally` 恢复 + 前后指纹（py 文件数 +
  总字节 + .pth 存在性）比对，不一致即报错。**每轮验证后均确认
  `30 个 py / 84973 字节 / .pth 在场` 复原一致**；
- **进程级在场探针**（`probe_bootstrap/sitecustomize.py`，链式保留原
  sitecustomize）：每个训练 worker 启动时记录 `xswift_importable` /
  `import_hooked_by_xswift` / `sys.modules` 里的 xswift 模块 /
  `/klx_dummy_lib` 痕迹。**不只看 rank0 banner**。

读法（关键）：

- **`loss` 逐位一致 ≠ checkpoint 正确**。moe_lw1 的两个状态 loss 100% 逐位一致、
  exit=0，但导出的 181 个张量是 3.7e33 垃圾值。这是本轮最该记住的一条：
  **退役验收必须比对导出权重，不能只看 loss**；
- dense_final 的 `hf_bitwise=True` 是**假安全**：dense 走 LoRA，HF 只导出 adapter，
  base 权重根本不在导出集合里，所以 `lm_head` 污染被完全掩盖。MoE full-tuning
  才暴露出来。**LoRA 口径不能用来证明退役的 checkpoint 安全**；
- 第一轮（未关 BF16 pin）的 dense 一度出现 372/372 全污染（max 1.0e34），
  加 `XTE_DISABLE_FAST_BF16_CACHE=1` 后 372/372 转为逐位一致——这与 big_leaf
  设计文档 §9.2 记录的「TE BF16 pin 在 forward 原地覆盖 Parameter 导出视图」
  完全吻合，是同一机制在 XSwift 退役场景的复现。

**污染归因（逐项消元，每项独立一次完整训练）：**

| 配置 | 专家权重污染 | `lm_head` 污染 | 与 plugin_on 逐位一致 |
|---|---|---|---|
| LW=1，pin 开，mem-eff 开 | 372/372（dense adapter 亦污染） | — | 0/372 |
| LW=1，**pin 关**，mem-eff 开 | **180** 个 expert 张量 | 1 | 50/231 |
| **LW=0**，pin 关，mem-eff 开 | **0** | 1 | 230/231 |
| **LW=0，pin 关，mem-eff 关** | **0** | **0** | **231/231** |

三个变量互相独立，各自解释一类张量：pin → 全体（含 adapter）、
LW=1 → MoE 专家权重、mem-efficient → `lm_head`。

### 16.4 推翻的两条既有结论

#### A. B6「Evaluation 厂商模式保护」不能关闭（§5 与 §9 队列第 5 项需改写）

§5 的结论是：`HYDRA_DISABLE_FAST_FC_MEMORY_EFFICIENT` 在「生产 swift+megatron 路径
（XME/XSwift 均关）linear 不经 hydrax fc_fusion，此 env 在生产为 no-op」，因此
XSwift 的 evaluate wrapper「不承接」。

**实测推翻**：在 XSwift 包物理移除、LW=0、pin 已关的配置下，`lm_head.weight`
导出为 3.7e33；显式加 `HYDRA_DISABLE_FAST_FC_MEMORY_EFFICIENT=1` 后同一配置
变为 231/231 逐位一致。即该 env **在生产形态下有真实作用对象**，XSwift 的
evaluate wrapper 正是在挡这个问题。

与 §5 旧实验不矛盾的解释：旧实验（`experiments/b6_fast_fc_mem_efficient/`）测的是
**hydrax linear 本体的数值与显存**，结论「两态数值逐位一致」在 forward 输出层面
成立；它没有测**参数存储被原地覆写后再导出 checkpoint** 这条路径。旧结论的适用
范围被错误外推了。

**行动**：B6 从「已关闭」改回**打开**。但承接方式不必照搬 XSwift 的 evaluate
wrapper——更简单的是在生产 `env.sh` 固定 `HYDRA_DISABLE_FAST_FC_MEMORY_EFFICIENT=1`
（代价：按 §5 实测为峰值显存 +224/448 MiB per 相关张量、速度 ~1.00x）。
若要保留 mem-efficient 的显存收益，则必须由某一层在 save 之前保证参数存储干净，
这就回到 XSwift wrapper 的等价实现。

#### B. §15.4 的「退役路径不闭合」过于悲观

§15.4 的推理链是：生产 LW=1 → XSwift 的 B2/B3 shim 承重 → 要退役须先关 LW →
但 big_leaf 与 LW=1 互斥且 LoRA 形态零收益 → **无闭合解**。

**实测修正**：这条链的第二环需要细化。关闭/移除 XSwift 后，在 LW=1 下
`_set_mlp_state` **并没有抛 `AttributeError`**（XME 的 `__getattr__` 视图使
`weight{i}` 可读，XME 在生产仍开启），而是**静默导出垃圾值**。所以：

- 「shim 承重」成立，但失败模式比文档预期**更危险**（静默 vs fail-fast）；
- 「无闭合解」不成立：**关 LW（`XTE_GROUPED_GEMM_LARGE_WEIGHT=0`）即可干净退役**，
  实测 231/231 逐位一致。代价是放弃 LW=1 的 MoE 性能收益（按
  `klx_large_weight_特性全链路分析` 为 MoE 层 ~12-14%），而 big_leaf 在生产
  默认的 LoRA 形态下补不上（B14）。

**这是一个纯粹的取舍，而不是技术死锁**：要退役 XSwift 就要接受 LW=0 的 MoE 性能，
或者先把 big_leaf 的 LoRA 形态补齐（B14）再退役。

### 16.5 性能结果：噪声带内，无方向性退化

边际 s/it 中位数（去 10 步 warmup），`base/other` >1 表示退役后更快：

| 形态 | plugin_on（基线） | plugin_off | pkg_removed | 判定 |
|---|---:|---:|---:|---|
| dense（最终配置，100 步） | 0.9657 s/it | 0.9275（**1.041x**） | 0.9448（**1.022x**） | 退役后略快 |
| dense（pin 关，100 步） | 0.9267 s/it | 0.9568（0.969x） | 0.9218（1.005x） | 方向不一致 |
| MoE（最终配置，100 步） | 0.0975 s/it | 0.0971（1.004x） | 0.1007（0.968x） | 方向不一致 |
| MoE（LW=0，60 步） | 0.0947 s/it | 0.0941（1.007x） | 0.0942（1.006x） | 持平 |

**结论：XSwift 的在场与否对整网步时没有可分辨影响。** 四组里 `plugin_off` 与
`pkg_removed` 相对基线的比值在 0.968–1.041x 之间双向漂移、同一配置下两个状态
方向都不一致，说明观测量级（±4%）小于本机运行间噪声。

峰值显存三状态**完全相同**（dense 36.71 GiB、MoE 2.75 GiB），说明退役不改变
显存水位。注意 `memory(GiB)` 是 `max_memory_reserved` 经 MP 组 reduce_max 的
聚合值，不能横向比较各卡。

**不宣称性能收益或退化**：要给出可信的性能结论需要同配置多轮交替（参照
big_leaf §12.2 的交错采样口径），本轮每配置每状态只跑一次，只能支持
「无方向性退化」这个弱结论。

### 16.6 验证过程中踩到的三个环境机制坑（已修，值得固化）

都不是 XSwift 的问题，但都会让退役验证**拿到看似通过的无效证据**：

1. **`~/.bashrc:129` 覆盖 `RUNTIME_SCRIPT_DIR`**（最严重）：
   `export RUNTIME_SCRIPT_DIR=/root/dl/runtime/script` 把 `run.sh` 自己在 line 20
   算出的目录顶掉，于是 line 132 的 `source "${RUNTIME_SCRIPT_DIR}/env.sh"` 读的是
   **生产 env.sh**（硬编码 `XSWIFT_PLUGIN_ENABLE=1`），外部传入的 0 被吃掉。
   **后果：第一轮「plugin_off」实际上 XSwift 全程在场并重写了全部 18 个符号**，
   banner 在日志里明明白白，但如果只看 exit=0 和 loss 一致就会得出完全错误的结论。
   该轮数据已作废并标记为 `dense_INVALID_bashrc_override/`。
2. **`~/.bashrc` 重新 export 全部 `HUNYUAN_*`**：外部设 `HUNYUAN_CKPT_PATH` 无效，
   训练产物会写进**生产 ckpt 目录**。本轮前 4 次冒烟即如此（见 §16.7 待清理项）。
   脚本副本改用 `TTV_<VAR>` 前缀在 bashrc 之后重新应用。
3. **swift 的 `v{N}-{时间戳}` 版本子目录**：`logging.jsonl` 与 `checkpoint-N` 落在
   `output/v0-…/` 而非 `output/`，直接拼路径会静默拿不到 metrics。

对应的三道硬断言已写进验证器，任何一条不满足直接 `RuntimeError`，不再可能
静默产出无效结论：

| 断言 | 拦住什么 |
|---|---|
| `banner_present == (state == "plugin_on")` | 开关没真正生效（坑 1） |
| worker 探针 `XSWIFT_PLUGIN_ENABLE` 全为 `0`（非 plugin_on 时） | 同上，且覆盖 rank0 之外的 worker |
| `pkg_removed` 下 `any_importable == False` | 包没真移走 |
| exit=0 时 `run_dir/output` 必须存在 | 产物落到生产目录（坑 2） |
| 包移除前后指纹一致 | 环境被破坏 |

### 16.7 结论、推荐配置与未覆盖边界

**可以退役。** 推荐的生产 `env.sh` 改动（三行）：

```bash
export XSWIFT_PLUGIN_ENABLE=0                     # 或直接移除包
export XTE_GROUPED_GEMM_LARGE_WEIGHT=0            # 必须：否则 MoE 专家权重导出为垃圾值
export HYDRA_DISABLE_FAST_FC_MEMORY_EFFICIENT=1   # 必须：否则 lm_head 导出为垃圾值
```

同时建议保留 `XTE_DISABLE_FAST_BF16_CACHE=1`（本轮全部验证都带它；它是 big_leaf
正式入口的强制项，也是第一轮 dense 372/372 污染的解）。**三者缺任一都会产生
静默损坏的 checkpoint。**

未覆盖/不宣称：

| 项 | 状态 |
|---|---|
| 真实大 MoE（35B-A3B 级）BF16 | 未覆盖——本机可见 MoE checkpoint 全为 FP8 |
| LW=1 下的干净退役 | **不可行**（专家权重导出污染）；要么关 LW，要么承接 B2 shim |
| 多机（NNODES>1）、TP/PP/CP>1 | 未覆盖，本轮均为单机 DP4/EP4、TP=PP=CP=1 |
| 长稳训练与模型效果 | 未覆盖，最长 100 步；不做任务效果评测 |
| 性能的强结论 | 不宣称；每配置每状态仅一次运行，只支持「无方向性退化」 |
| optimizer/RNG resume | 未覆盖（生产默认 `no_save_optim/rng=true`） |
| XME 退役 | 不在本轮范围；**XME 全程开启**，且 LW=1 下专家权重可读依赖 XME 的 `__getattr__` |

**遗留待清理**：第 2 个坑导致 4 次冒烟训练把产物写进了生产 ckpt 目录
`$HUNYUAN_CKPT_PATH`（`v0-20261118-224645`、`v1-225108`、`v2-225940`、
`v3-230313`，约 1.7 GB）。**已于 2026-11-19 经用户授权删除**，该目录现仅剩
`runs` 符号链接与 `v4-20261119-002741`、`v5-20261119-002952`（非本轮产物，未动）。

### 17.1 B17：状态为什么必须运行期复核

`_APPLIED` 是**安装那一刻**的结论，而厂商插件的 `KlxSymbolRewriter.replace()`
是整函数替换，可以在之后把同一符号整体顶掉——生产的真实顺序正是
`activate()` 先打补丁、再 import swift 触发厂商 lazy hook。

修复后在真实栈上复测（`XSWIFT_PLUGIN_ENABLE=1`，两种顺序各一次）：

| 顺序 | 安装时状态 | 复核后状态 |
|---|---|---|
| `tt_first`（生产顺序） | 三项全 `applied` | `wrap_model` → `overwritten(xswift_ext...wrap_model)`、`gather_object` → `overwritten(xswift_ext...gather_object_cpu)`、THD 仍 `applied` |
| `xswift_first` | `wrap_model`/THD 为 `skipped`、`gather_object` 为 `applied` | 同左（无覆盖） |

**`patch_status()` 与 `assert_bindings_intact()` 是两个口径，不是同一件事**
（2026-11-19 实测澄清，此前表述为"逐项对账一致"**不准确**）：

| 报告 | 问的问题 | 判据 |
|---|---|---|
| `patch_status()` | TT 的修正**是否仍在调用链上生效** | 身份相等**或**当前对象把我们包在 `__wrapped__` 链里 |
| `assert_bindings_intact()` | 落点对象**是否还是绑定那一刻那个** | 严格身份相等 |

`tt_first` 下 tampered=4 而 overwritten 只有 2 条，差额正是 THD 与
`_apply_rotary_pos_emb_bshd`。THD 的实测形态（逐项取证）：

```
快照 owner      : fwpatch
快照对象 is 当前: False          ← bindings 据此报 tampered
_wraps_object   : True           ← patch_status 据此仍报 applied
cur             : mcore_bridge.patcher _patch_mrope.<locals>._apply_rotary_pos_emb_thd
cur._tt_patched : True
```

原因是 `mcore_bridge.patcher._patch_mrope()` 在 TT 打完补丁**之后又被调用一次**，
用 `functools.wraps` 把当时的实现（= TT 的 wrapper）包了一层。TT 的修正仍在链上，
报 applied 正确。**这是 §17.1 第 2 条守卫在真实环境的首次命中**——没有它，THD
会被误报 `overwritten`，而 big_leaf 入口的 fail-fast 直接读这个状态，
会把一个完全正常的训练打挂。

两个设计取舍（都写进了代码注释）：

1. **复核不改写 `_APPLIED`**，也不自动重打补丁——"被顶掉后谁该赢"是语义决策，
   不该由一次状态查询顺手做掉；
2. **第三方在我们外面再套一层**（`functools.wraps` 形态，`__wrapped__` 链上
   仍能找到我们）不算覆盖。TT 的修正此时真实生效，报 `overwritten` 是假警报，
   而 big_leaf 入口的 fail-fast 直接读这个状态——假警报会把能正常跑的训练打挂。

生产入口的那一眼**刻意不 raise**：过渡期厂商实现本身就在干同一件事
（如 `wrap_model` 的双栅栏），把它判为致命错误会误伤。要的是失效可见与归因正确。

### 17.2 B18：归因反了比不接管更危险

旧判据只看源码 needle `ddp_stream`，而 XSwift 的 `wrap_model` 替换实现是
swift ≥4.3.2 的**逐字拷贝**、变量名恰好就叫 `ddp_stream` → TT 判「上游已修复
→ 不接管」并如此留痕。两者的退役含义完全相反：**厂商在场**意味着退役后缺口
会回归，**上游已修复**意味着补丁可以永久删除。

修复后在真实栈复测（`xswift_first`）：`wrap_model` 与 THD 的 provenance 均为
`reason=vendor_plugin_present, vendor=xswift_ext`，不再写成上游修复。

顺带查清一件事（本轮新事实）：`xswift_first` 下 THD 的判定从 `applied` 变为
`skipped`，原因是 XSwift 连 `mcore_bridge.patcher` 一起换成了自己的拷贝
（`__module__` 仍报 `mcore_bridge.patcher`，但 `co_filename` 在
`xswift_ext/components/`）——而**那份拷贝自带 cp_group 回退**
（`components/mcore_bridge/patcher.py:110-115`，与 B1 修法一致），
所以不接管是安全的。插件关闭后复测 3/3 `applied`，B1 的补丁照常生效。

### 18.4 闸门挂载点的修正

实施 §17 时闸门只挂在 `big_leaf/swift.py::enable()`，而 `ttorch.activate()`
**只有在显式设置 `TT_BIG_LEAF` 时**才会调它（`ttorch/__init__.py`）。
生产退役路径是 `megatron sft` + `.pth` 自动激活且不设 `TT_BIG_LEAF` ——
闸门在那条路径上根本不触发，等于装饰品。本轮改为：

- `ttorch.activate()` 对**训练 worker**（`RANK`/`LOCAL_RANK` 在场）执行契约；
- 契约失败抛 `ExportUnsafeError`，`utils/_auto_init` 把它转成 `SystemExit`
  —— `.pth`/sitecustomize 路径的普通异常会被 `site` 吞成一行警告、训练照跑，
