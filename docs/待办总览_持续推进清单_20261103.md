### B.1a large-weight 三条的处置：**不迁入 TT，单独设计方案**（2026-11-04 用户决策）

**决策**：B2/B3/B4 既然**只在主动开启 large-weight 时才存在**，就不按「XSwift 功能迁移」
的路子搬进 TTorch，而是**后续单独设计方案实现**。

**决策依据**：

1. **不是「硬件/框架缺口」，是「一个可选开关的代价」** —— 开关默认 False
   （`xmegatron_ext/envs.py:68`），厂商源码自标「temporary solution，need to be removed

   在 TT 里建长期兼容层，方向不对。
2. **迁进 TT 会污染 TT 的职责边界** —— shim 要替厂商维护「3D 合并参数 ↔ per-expert
   视图」的映射，这是**厂商权重布局的实现细节**，不属于 TT 的「功能接入」语义。
3. **还剩 C1 这个高危项**（优化器 `param_state` 裸索引重排，错位不可检测）——
   继续迁移路线必须连它一起吃下，风险最高的一块反而要 TT 背。
4. **单独方案的空间更大**：可以选「关开关」「向厂商提需求」「在 swift/mcore_bridge 侧
   统一参数契约」等，不被 TT 的补丁形态限制。

## 维护约定

1. 每轮只推进一个功能点，验证后更新该条状态，不以条目数或代号完成数判断进度。
2. 勾销需三件齐备：源码修改 + 回归测试 + 实测证据。文档结论不等于代码已修。
3. 新增缺口按组追加 ID，不复用已勾销的 ID。
4. 「暂缓」项若出现新触发证据，移回待修并注明触发来源；无新证据不写猜测式 patch。
5. 功能兼容与性能接管分开登记，各自记录来源、适用范围、版本与验证结果。
6. 跨硬件/跨框架对比先对齐变量（trainable params、batch、cutoff_len、库版本矩阵）；
   速度用边际 s/it，不用累计平均；短任务不用 `train_runtime` 比硬件。
7. **回归测试必须经红绿校验**（2026-11-04 新增，来自 A1 的真实教训）：断言必须对
   「修复前的代码」为**假**。A1 首版断言 `speedup < 1.0` 对修复前后**都成立**
   （autograd.Function 的 Python 调度开销让仅-fwd 口径也只有 0.38）——测试过了但
   什么都没证明。改为比较两种口径的比值后红绿才成立。
8. **区分「症状已修」与「根因已消除」，并先问「这个根因该归谁」**（来自 B2/B3）：
   B2/B3 的补丁写完才发现，三条症状都只在**一个可选开关打开时**才存在 ——
   这类问题不该按「功能迁移」塞进 TT，而应单独立项。**动手前先判断触发条件是
   「常态」还是「某个开关的代价」**，后者往往不属于兼容层的职责。
9. **「已知局限、暂不修」必须经实测确认是局限而非当场的 bug**（来自类方法落点那条）：
   我曾把「类方法快照 key 不含模块路径」登记为已知局限，实测证明它当场就打断整个
   完整性检测。登记局限前先跑一遍。
