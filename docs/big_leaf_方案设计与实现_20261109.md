## 0. 最终交付速览

### 0.1 用户使能与默认行为

在目标生产脚本目录只需：

```bash
TT_BIG_LEAF=1 bash run.sh
```

| 总开关状态 | 最终语义 |
|---|---|
| `TT_BIG_LEAF=1` | 选择 TTorch big_leaf；在 Megatron DistributedOptimizer 路径自动接入 DDP layout、main_grad 和生命周期，复用原 optimizer/checkpoint 逻辑契约 |
| 显式 `TT_BIG_LEAF=0` | stock A/B；worker 安装相同的 fast-FC 生命周期，只隔离布局变量 |
| 完全未设置 | 普通 stock，不引入 big_leaf 入口 |

生产只保留这一个功能开关，固定使用 `patch` forward。fast-FC 生命周期自动安装，
默认 `XMLIR_ENABLE_FAST_FC=1` 和 `XTE_DISABLE_FAST_BF16_CACHE=1`；显式 pin-on
直接拒绝。原 `TT_MEGATRON_ENTRYPOINT`、`TT_BIG_LEAF_FORWARD_MODE`、
`TT_FAST_FC_LIFECYCLE` 均已删除。`switch` 仅留在底层研究 API，不再是生产配置。

总开关只负责功能接线，**不改变 checkpoint 保存/加载策略**。完整 optimizer/RNG
resume 和 stock↔big fully-reshardable 验收还需 `NO_SAVE_OPTIM=false`、
`NO_SAVE_RNG=false`、`NO_LOAD_OPTIM=false`、`NO_LOAD_RNG=false` 及
`DIST_CKPT_OPTIM_FULLY_RESHARDABLE=true`；当前生产脚本的保存/格式默认值为
`NO_SAVE_OPTIM=true`、`NO_SAVE_RNG=true`、fully-reshardable=`false`，并不属于完整
lifecycle 口径，验收器会显式设置上述完整配置。

### 0.2 先分清：是否使用 Megatron DistributedOptimizer

`DistributedOptimizer`（下文偶尔缩写为 `dist-opt`）是 Megatron 的分布式优化器：
它按数据并行 rank 分片维护 FP32 主权重和 Adam 等优化器状态，反向后以梯度
ReduceScatter 取代全量 AllReduce，本地更新分片后再 AllGather 参数。它不改变 Adam
数学公式，也不等于 FSDP；标准 DDP + DistributedOptimizer 仍保留完整模型参数和
梯度 buffer。

当前环境的 ms-swift 将 `use_distributed_optimizer` 默认设为 `True`（Muon 例外，会
强制关闭）。因此裸跑 `megatron sft ...` 通常默认使用 DistributedOptimizer，但
**不会因此默认启用 big_leaf**。big_leaf 只在 TTorch 已激活且显式设置
`TT_BIG_LEAF=1`，或生产脚本据此选择 `python -m ttorch.bridge.big_leaf.swift`
包装入口时生效；该入口遇到 `use_distributed_optimizer=False` 会直接拒绝。

big_leaf 实际包含两条集成路径，不能混用 optimizer 参数数量、checkpoint 和性能口径：

| 维度 | 不使用 DistributedOptimizer：手工普通优化器路径 | 使用 DistributedOptimizer：正式自动入口 |
|---|---|---|
| 典型入口 | `apply_big_leaf()` + `plan.optimizer_params()` / `optimizer_param_groups()` | `TT_BIG_LEAF=1 bash run.sh`，由 TTorch 包装 ms-swift/Megatron CLI |
| 分布式要求 | 不依赖 Megatron DistributedOptimizer；主要验证为单机/model-space，但“不使用”不必然等于单机 | 强制 `use_distributed_optimizer=True`，复用 Megatron DDP 和 optimizer |
| forward / autograd | 每层一个 plain-tensor `big_leaf`，整体 `dw` 进入 `big_leaf.grad` | 相同 |
| optimizer 更新实体 | 每层一个 `big_leaf`（含 bias 再加一个），替代 G 个原专家参数 | **不把 big_leaf 交给 optimizer**；仍由原 `weight{i}` 对应的 DDP 参数和 owned shard 更新 |
| 梯度路径 | 普通 optimizer 直接消费 `big_leaf.grad` | `big_leaf.grad → 原 main_grad → DDP 规约 → owned shard`，每步有显式 flush |
| 模型 checkpoint | 保持 `weight{i}` / `bias{i}` 注册键和值 | 相同 |
| optimizer checkpoint | 内存中是合并后的大 state；stock/LW=1↔big 或 big→stock 需要 `convert_optimizer_state_dict()` | fully-reshardable 按原逻辑参数名保存/恢复，**不调用普通 optimizer converter**；其他依赖旧 DDP 物理布局的格式不自动兼容 |
| 主要性能收益 | forward host/cat、backward 拆分、**optimizer 单实体**三类收益都保留 | 保留 forward host/cat 和主要 backward 收益；**不完整获得 optimizer 单实体及 DDP 元数据缩减收益** |
| 外部适配成本 | optimizer 构造、grad clip、optimizer resume 仍需 big_leaf API；不是全链路无感 | 原 optimizer/checkpoint 逻辑契约保留，但 DDP layout、main_grad、LoRA/load 守卫仍需 TTorch 接管 |
| restore | clone 回独立参数存储，之后必须重建 optimizer | 只摘除 big_leaf/hooks，保留 DDP 参数视图、`param_data` 和 optimizer |

因此，**“不改 optimizer/checkpoint 逻辑格式”与“拿到 LW=1 的全部性能收益”不可
同时宣称**。正式自动入口是用 optimizer 单实体收益换取 Megatron 原契约；手工普通
优化器路径更接近完整 LW=1 性能机制，但支付显式 optimizer/checkpoint 适配成本。

### 0.3 生产自动接线


## 1. 方案逻辑：收益来源与路径取舍

### 1.1 问题定义

TE `GroupedLinear` 以 G 个独立 `weight{i}` 参数注册专家权重（LW=0）。厂商
`large_weight`（LW=1）把它改成单个 3D Parameter，在 MoE 层拿到 ~12-14% 收益，
但注册变更迫使 Megatron / mcore_bridge / LoRA tuner / dist-ckpt 四条链路打
兼容补丁（L0-L8 shim 链）。**目标：不改模型注册键，尽量回收 LW=1 的主要收益；
不同 optimizer 路径保留哪些收益必须分别论证，不预设全面反超。**

### 1.2 收益的真实来源（微分实验实证，`probe_slow_path_trigger.py` 等）

先纠正一个关键误判——LW=1 的优势**不在 kernel**：

| 假设 | 实测 |
|---|---|
| kernel 对视图张量有慢路径惩罚 | 否。pin 缓存命中时 Parameter/plain/view 同速（~1920us）；所谓「视图惩罚」实为 cat 拷贝 |
| pin（原地 pack）路径更快 | 否。生产形态（每步失效重 pack）pin 2067us 比 fresh pack 1910us **慢 ~160us**；pin 的价值是显存（B6） |
| 合并 grouped GEMM 比逐专家快 | 是（1.21x），但 LW=0/LW=1 共享该 kernel，非差异来源 |

LW=1 的真实收益三处，全部在 kernel 之外：

1. **host 收集开销（~470us/层）**：LW=0 每步 `getattr(weight{i})`×8 +
   `unsqueeze`×8 + `noop_cat` 地址连续性校验（+bias 同套）；LW=1 一句
   `getattr(self, "large_weight")` 全免；
2. **backward 梯度拆分（~90-180us/层）**：`dw` 要 narrow+accumulate 成 G 份回
   各 `weight{i}.grad`；LW=1 一体进 `large_weight.grad`；
3. **optimizer 参数数（普通 TE FusedAdam 孤立口径 ~162us/层，foreach 口径 ~513us）**：
   16 参数 vs 2 参数。该数字不是 DistributedOptimizer 整网固定收益。

### 1.3 big_leaf 的对应解法

连续 buffer 和布局信息由 TTorch 自持有，前两类收益在两条路径都能回收；第三类
收益取决于 optimizer 是否直接持有 big_leaf：

| 收益源 | big_leaf 的回收方式 |
|---|---|
| host 收集 | 一次性建好 `big_leaf`，`patch` forward 直递，不再每步收集/探测 |
| backward 拆分 | `big_leaf` 是 autograd 叶子，`dw` 一次 accumulate 进 `big_leaf.grad`，不做 G 份 autograd 拆分；DistributedOptimizer 路径仍有 main_grad flush |
| optimizer 参数数 | 手工普通优化器路径用 `big_leaf` 替代 `weight{i}`，拿到单实体收益；DistributedOptimizer 路径保留原参数及 shard 映射，**没有完整拿到这项收益** |

外加继承自 repack 的零拷贝（消除每步真 cat 拷贝 ~250us，在 host-bound 路径下被掩盖）。

## 2. 关键设计点

### 2.1 `big_leaf` 必须是 plain tensor，不能是 `nn.Parameter`

厂商 kernel 的 pin 快路径门槛是 `isinstance(w, Parameter)`
（`grouped_linear.py:278`），且 `memory_efficient=True` 的语义是**别名参数存储
并原地覆写**（`env_config.py:230-244` 注释明写，靠 optimizer 每步"自愈"）。
若 big_leaf 用 Parameter：进 pin 路径 → 原地覆写 buf → **1 步即污染全部
weight{i}**（实测复现）。用 plain tensor：走 fresh pack 路径，无原地改写，
且实测 fresh pack 不慢于 pin（生产形态下反而快 ~160us）。

### 2.2 `weight{i}` 只承担「注册/报键」职责，计算全程不碰

`w.data = buf[i]` 重绑后：Parameter 对象身份不变、state_dict 键不变、TP 属性
保留、save/load 走视图读 buf 最新值（dist-ckpt/HF 导出全链路逐位验证）。
它们不进 autograd 图（grad 为 None 是设计使然）。

### 2.3 AdamW 逐元素等价性 = 合成更新的数学基础

AdamW 是纯逐元素算子（lr/wd/betas/eps 均标量），同 param group 下合并更新 ≡
逐片更新。实测不止数学等价——合成 1 参数 vs 逐 8 参数的 3 步轨迹（grad+权重）
**逐位一致**。weight decay 作用整个 buffer 与逐片同理等价。

### 2.4 显存中性 + 显式时序约束

- repack 时 `w.data` 重绑使旧 storage 引用归零即释放；**不持有回滚用的旧
  storage**（否则常驻 2×，评审 D1 修复）。apply 后常驻显存增量 <1MiB（C9 断言）。
- 手工普通优化器路径：在「`model.to(device)`/dtype 转换 + load 权重完成之后、
  optimizer/DDP 构建之前」apply；DistributedOptimizer 正式入口则由 DDP wrapper
  自动在构造前 prepare、构造后 attach，用户无需处理时序。禁止
  `load_state_dict(assign=True)`，非法生命周期会 fail-fast。

### 2.5 可靠性设计：fail-fast，无静默路径

- `assert_healthy()`：weight/bias ptr 连续性、large_weight 身份、switch 状态、
  leaf 状态逐项断言；
- 重复 apply 显式拒绝（幂等保护，防止 optimizer 引用静默失效）；
- 手工普通优化器 `BigLeafPlan.restore()`：`clone()` 写回独立参数存储，保留训练更新，
  之后必须重建 optimizer；`BigLeafMegatronPlan.restore()` 只摘除 big_leaf，
  保留 DDP 参数视图和 optimizer，不恢复独立 stock storage。

## 3. 代码逻辑与核心代码

### 3.1 数据结构：一个模块一条绑定

```python
@dataclasses.dataclass
class _LeafBinding:
    module: GroupedLinear
    buf: torch.Tensor            # 权重连续存储本体 (G, out, in)
    bbuf: Optional[torch.Tensor] # bias 连续存储（无 bias 为 None）
    big: torch.Tensor            # 权重 big_leaf（plain leaf，非 Parameter）
    big_b: Optional[torch.Tensor]
    # 刻意不持有 repack 前旧 storage（显存中性）；restore 按需新分配
```

`BigLeafPlan.bindings` 持有全部绑定，向外提供 `leafs / optimizer_params /
named_leafs / grad_tensors / assert_healthy / restore` 六个接口。

### 3.2 repack：唯一的存储变更点

```python
def _repack_one(mod):
    ws = [getattr(mod, f"weight{i}") for i in range(mod.num_gemms)]
    buf = torch.empty(len(ws), *ws[0].shape, device=ws[0].device, dtype=ws[0].dtype)
    with torch.no_grad():
        for i, w in enumerate(ws):
            buf[i].copy_(w)        # 值逐位搬入连续 buffer
            w.data = buf[i]        # .data 重绑：Parameter 对象身份/state_dict 键不变
    # plain leaf：共享存储、非 Parameter；继承原参数的冻结/可训语义
    big = buf.detach().requires_grad_(ws[0].requires_grad)
    # bias 同套（bbuf/big_b），无 bias 跳过
    return _LeafBinding(mod, buf, bbuf, big, big_b)
```

### 3.3 安装路径：生产固定 patch，switch 仅供底层研究

手工普通优化器路径可显式调用 `apply_big_leaf(model, forward_mode="patch")`；
DistributedOptimizer 正式入口不直接调用该函数，而由 `ddp_init_wrapper` 在 DDP 边界创建
`BigLeafMegatronPlan`。两条路径最终都通过 `_install_forward()` 安装绑定：

- **patch（生产唯一模式）**：保存 `module._big_leaf_binding`，设置
  `large_weight_switch=False`，将 `module.forward` 替换为自管理实现；普通
  `GroupedLinear` 和 Megatron `TEGroupedLinear` 分别保持原返回契约；
- **switch（底层兼容/研究）**：挂入 `module.large_weight/large_bias` 并打开
  `large_weight_switch`，复用厂商 forward 分支；生产环境不再提供该配置项。

生产 forward 数据流：
`inp → big_leaf patch forward → prepare_forward →
MoeFcFusionImpl.apply(inp, binding.big, ...)`。`weight{i}` 收集、unsqueeze 和
`noop_cat` 全部绕过，且不依赖原 LW 私有开关。

backward 数据流：`dw (G,out,in) → autograd 叶子 accumulate → big_leaf.grad`
（一次，无拆分）；`weight{i}.grad` 保持 None。安装后执行显式 `_require()` 健康检查；
可选 probe 进一步核对输出 shape 及权重 ptr/值没有被厂商路径原地改写。

### 3.4 optimizer 对接

```python
def optimizer_params(self, model):
    gl_param_ids = set()
    for b in self.bindings:
        for i in range(b.module.num_gemms):
            gl_param_ids.add(id(getattr(b.module, f"weight{i}")))
            if b.module.use_bias:
                gl_param_ids.add(id(getattr(b.module, f"bias{i}")))
    others = [p for p in model.parameters() if id(p) not in gl_param_ids]
    return others + self.leafs  # 非 MoE 参数 + weight big_leaf + 可选 bias big_leaf
```

- 任意逐元素 optimizer 可直接用（AdamW/TE FusedAdam/apex 均验证逐位轨迹）；
- 按名分组规则（muon/no-wd）用 `named_leafs(model)` 返回的
  `(模块限定名.large_weight, leaf)` 对接；
- grad clip 用 `grad_tensors()`（合并范数 ≡ 分立范数，C6 已证）。

以上 `optimizer_params()` 仅属于**手工普通优化器路径**。DistributedOptimizer
正式入口明确禁止调用它：DDP 继续持有原注册参数，optimizer 仍由
`get_megatron_optimizer(DDP)` 创建；`compute_full_param_layout()` 保证 canonical
连续布局。attach 后将 `big_leaf.grad` 累加到 canonical `main_grad` 视图，随后清
`.grad` 并触发原 DDP bucket 规约；DistributedOptimizer 在规约后消费 owned shard，
从而保持 optimizer/checkpoint 逻辑契约。其内部仍按原参数映射本地 shard，并未获得
手工路径的每层单 optimizer 实体。

### 3.5 回滚与巡检

手工普通优化器 `BigLeafPlan.restore()` 会将训练后的 buf 值 clone 回独立参数存储，摘除
forward/gradient hooks 并恢复 LoRA/load 包装，之后必须重建 optimizer。
`BigLeafMegatronPlan.restore()` 仅摘除 big_leaf forward/gradient hooks 和相关包装，
保留 DDP 参数视图、`param_data` 与 optimizer，**不 clone、不恢复独立 stock storage**。
生产格式回滚优先使用新进程和 fully-reshardable big→stock checkpoint，不在训练中途
更换 plan。

1. **生产使能**：已提供唯一 `TT_BIG_LEAF` 总开关和自动 DDP 接线；代理模型三轮
  200 步对 stock 的收益已实测，大型生产模型性能、长稳及对 LW=1 的同环境对比仍需复测；
2. **checkpoint 格式**：手工普通优化器路径的 stock/LW=1 resume 有显式转换层；
  DistributedOptimizer 路径已验证 `fully_reshardable` 的 stock↔big_leaf，无需普通
  optimizer converter。其他依赖 DDP 内部布局的旧格式、以及 LW=1 原生
  `large_weight` 格式直读，需先转 stock/per-expert canonical 格式；
3. **并行覆盖**：TP=2、EP=2 已整网逐位；TP=2×EP=2 因 stock 整网自身存在通信/
  缓存非确定性，采用真实分片算子逐位 + 单 big_leaf 整网训练 smoke。PP/VPP 未支持；
4. **其他执行引擎**：int8/fp8、FSDP、torch.compile 尚未验证，不能从 bf16 eager
  结论外推；delayed-wgrad、CUDA graph flush、LayerWise 为显式拒绝项；
5. **fast-FC 生命周期**：显式总开关入口默认启用 fast-FC，自动安装 TTorch
  optimizer-step/save/load 生命周期并关闭 BF16 pin，不再依赖 XME post-hook；
  绕过正式入口的裸 Megatron 链路仍需调用方自行保证缓存失效；
6. **DDP 配置限制**：自动入口不接受外部 `full_param_layout` 或自定义
  `pg_collection`，暂不支持多 dist-opt instance 及
  `reduce_scatter_with_fp32_accumulation`，这些组合均显式拒绝；
7. **更底层 custom-op**：当前仍复用 `MoeFcFusionImpl`，直调 custom-op 仅登记为
  profiling 触发的 B13，不属于当前支持能力或本次 PR 承诺。

## 6. LW=0、LW=1 与 big_leaf：真实实现对比

> 本节是后续逐项分析的统一基线。结论只覆盖上述已验证环境；「每层」均指
> 一个 TE `GroupedLinear` 模块。性能数字来自 `RESULTS.md` 的固定实验记录，
> 不同轮次的微基准不能跨表直接相加。

### 6.1 先对齐对象：注册参数、计算图叶子、optimizer 实体不是一回事

以下按**无 bias**计数；有 bias 时三组数量分别再增加 G、1、1 个 bias 实体。

| 方案 | 模块中注册的权重 | forward 实际喂给 grouped GEMM 的对象 | 计算图内接收权重梯度的叶子 | optimizer 更新的权重实体 |
|---|---|---|---|---|
| LW=0 stock | G 个 `weight{i}` Parameter | `noop_cat(weight0…weightG-1)` 的 3D 结果 | G 个 `weight{i}` | G 个 |
| LW=1 | 1 个 `large_weight` Parameter，shape=`(G,out,in)` | 直接 `getattr(self, "large_weight")` | 1 个 `large_weight` | 1 个 |
| big_leaf：手工普通优化器 | 仍是 G 个 `weight{i}` Parameter，但 `.data` 均为连续 `buf[i]` 视图 | plain tensor `big_leaf`，与 `buf` 共享存储 | 1 个 `big_leaf`；`weight{i}` 不进图、grad=None | 1 个 `big_leaf` |
| big_leaf：DistributedOptimizer | 同上；DDP 中保留原 Parameter 和 canonical layout | 同上 | 同上 | 原 `weight{i}` 对应的本地 shard；big_leaf 只经 main_grad 提供梯度 |

源码落点：

- LW=1 单参数注册：当前环境 `grouped_linear.py:764-794`；LW=0 逐专家注册：
  同文件 `:795-827`；
- forward 直取与收集/cat 分支：同文件 `:985-1013`；
- `noop_cat` 连续时构造视图、不连续时 `torch.cat`，backward 将梯度切片返回
  各输入：`module/_common.py:127-165`；
- big_leaf 的重绑、大叶子与 forward：`ttorch/bridge/big_leaf/core.py`；单机 optimizer
  过滤同文件，生产 canonical layout 与 shard flush 在 `big_leaf/megatron.py`。

`verify_leaf_structure.py` 在 G=8、无 bias 下的本轮实证：

| 形态 | 注册参数数 | 非空梯度张量数 | 梯度形态 |
|---|---:|---:|---|
| LW=0 | 8 | 8 | 8×`(384,512)`，分别落在 `weight0…weight7.grad` |
| LW=1 | 1 | 1 | 1×`(8,384,512)`，落在 `large_weight.grad` |

因此，「多个小叶子」是 **LW=0** 的形态，不是 LW=1。还要纠正另一个容易混淆的
表述：LW=0 不是「先分别算出 G 份 dw，再合并」；真实顺序是 grouped backward
先得到一个整体 `dw (G,out,in)`，再由 `_NoopCatFunc.backward` 切片并交给
autograd 分别 accumulate 到 G 个叶子。big_leaf 则让这个整体 dw 直接
accumulate 到唯一大叶子，**拆分从未发生**。

### 6.2 什么都不做：LW=0 stock 每步在做什么、消耗在哪里

以 fast FC 开、`XTE_USE_GROUPED_FC_FUSION=0` 的生产 grouped kernel 路径为例：

1. **forward host 收集**：逐个 `getattr(weight{i})`、逐个 `unsqueeze(0)`，再进入
   `noop_cat` 做 shape/dtype/device/stride/data_ptr 连续性检查；bias 同理；
2. **权重拼接**：stock 的 G 个 Parameter 默认是独立 storage，检查失败后执行真
   `torch.cat`，分配 `(G,out,in)` 输出并拷贝 G 份权重。若事先做过 route C
   连续化，`noop_cat` 可退化为零拷贝视图，但 host 收集与检查仍然存在；
3. **厂商内部 fresh pack**：`noop_cat` 的结果是 plain tensor，不是 Parameter，
   因此不进 Parameter pin 缓存路径；`MoeFcFusionImpl` 仍需把权重 pack 成 kernel
   内部布局。也就是说，stock 并不是「完全没有 pack」；
4. **backward**：先算整体 dw，再由 `noop_cat` 反向切片，autograd 分别累加到
   G 个 `weight{i}.grad`；有 bias 时再走一套 bias 梯度路径；
5. **optimizer.step**：optimizer 看到 G 个权重实体（含 bias 为 2G），按具体
   optimizer 实现支付 Python 分组、tensor list 处理和 kernel launch 成本。

主要成本项的独立测量如下。它们是不同微 benchmark 的归因，**不可简单求和**：

| 成本项 | 实测口径与量级 | 说明 |
|---|---|---|
| host 收集与模块周边 | 约 470us/层 | G8 2048→1536、8K tokens、bf16、有 bias，route C 与 LW=1 的 fwd+bwd 差；route C 已消除真 cat |
| 真 cat 拷贝 | 约 187-250us/层 | 两轮裸 `MoeFcFusionImpl` 微基准分别为 2097 vs 1910us、2173 vs 1925us；host-bound 场景下部分会被掩盖 |
| backward 梯度拆分 | 约 90us（无 bias）/180us（有 bias） | 来自 narrow/切片返回与向各叶子 accumulate 的小 kernel/调度成本 |
| optimizer 多参数 | 强依赖实现 | G8 weight+bias 的 16 vs 2 参数孤立测量见 §6.6.2，不能套用单一固定数字 |

若 fast FC 关闭，会走逐专家 `_Linear` 路径；若
`XTE_USE_GROUPED_FC_FUSION=1`，会走 list 接口。这两条路径不能用本节的
`MoeFcFusionImpl` 数字解释。

### 6.3 LW=1 做了什么优化，拿到了什么收益

LW=1 在**建模时**直接改变参数注册：不再创建 G 个 `weight{i}`，而是创建一个
独占的 3D `large_weight` Parameter。它带来三项直接收益：

| 优化点 | 行为变化 | 拿到的收益 |
|---|---|---|
| forward 直取 | switch 分支只取 `large_weight`/`large_bias` | 消除逐专家 getattr、unsqueeze、noop_cat 检查和真 cat 拷贝 |
| 单一 autograd 叶子 | 整体 dw 直接进 `large_weight.grad` | 消除向 G 个小叶子拆分/累加的反向成本 |
| 单一 optimizer 实体 | optimizer 只看到 `large_weight`（含 bias 再加 1 个） | 降低参数数量相关的 host 与 launch 开销 |

合并 grouped GEMM 大算子本身**不是 LW=1 独有收益**：LW=0 stock 经 cat 后同样
调用 `MoeFcFusionImpl`。LW=1 的优势是更便宜地向同一个大算子提供权重，并以
同样粒度接收梯度、执行更新。

LW=1 的 Parameter 身份还会触发厂商 **pin/pack 缓存路径**：

- 首次 forward 对 `large_weight` 做 stateful pack，并缓存转换后的内部布局；
- eval/冻结等权重不变场景可以命中缓存，避免后续重复 pack，这是 LW=1 的潜在
  优势，但本文没有做推理性能 benchmark；
- 训练时 optimizer 更新权重后缓存必须失效，下一次 forward 重新 pack。独立
  微基准记录的重 pack 代价为约 **112-160us/层/步**，数值随 shape、脚本和
  测量轮次变化；
- trainable 且 `memory_efficient=True` 时，厂商语义是别名参数 storage 并原地
  覆写 packed 值。它的价值主要是少保留一份权重/packed 副本，不是必然提速。

这些收益的代价是**参数命名与注册契约改变**：Megatron/mcore_bridge/LoRA/
dist-ckpt 需要 L0-L8 兼容补丁；不同保存路径还可能出现 `weight{i}` 与
`large_weight` 的盘上格式分叉。

### 6.4 big_leaf 做了什么，拿到与没拿到哪些收益

big_leaf 的目标是在**保留 LW=0 注册键**的前提下，主动构造接近 LW=1 的计算
和梯度粒度；更新粒度则随两条 optimizer 路径不同，不能笼统写成完全相同。

**apply 时只做一次：**

1. 为每个 `GroupedLinear` 分配连续 `buf (G,out,in)`，把 G 份权重复制进去；
2. 执行 `weight{i}.data = buf[i]`，Parameter 对象、state_dict 键和 TP 属性不变，
   旧独立 storage 不再被 plan 持有；
3. 构造 `big_leaf = buf.detach().requires_grad_(原权重.requires_grad)`，它是
   plain tensor，不是 `nn.Parameter`；
4. 生产安装 patch binding 和自管理 forward，保持 `large_weight_switch=False`；
   底层 switch 仅用于研究兼容。有 bias 时对 bias 重复同样过程。

**之后每个训练步：**

| 阶段 | big_leaf 的真实行为 | 是否拿到收益 |
|---|---|---|
| forward host | 直取 big_leaf，不收集 weight{i}、不 unsqueeze、不 noop_cat | 拿到 host 收集消除收益 |
| 权重拼接 | big_leaf 本身就是连续 `(G,out,in)`，无需 cat | 拿到真 cat 拷贝消除收益 |
| 厂商内部 pack | plain tensor 仍走 **fresh pack**，每次 forward 从当前 buf 生成 kernel 内部布局 | **没有消除 fresh pack**；只是避开 Parameter pin 缓存与训练态重 pack 溢价 |
| backward | 整体 dw 一次 accumulate 到 big_leaf.grad | 拿到 autograd 梯度不拆分收益；DistributedOptimizer 路径随后仍要 flush 到 main_grad |
| optimizer：手工普通优化器 | optimizer 直接更新 big_leaf | 拿到每层单 optimizer 实体收益 |
| optimizer：DistributedOptimizer | 保持 `get_megatron_optimizer(DDP)`，原参数映射 owned shard | **不完整拿到单实体及 DDP 元数据缩减收益**；换取原 optimizer/checkpoint 逻辑契约 |
| checkpoint | state_dict 仍从 weight{i} 视图读 buf 最新值 | 模型键集合保持 stock 形态；optimizer checkpoint 按 §0.2 分路径讨论 |

DistributedOptimizer 会遍历原 `weight{i}`，为它们分别建立本地 shard 并交给内部
Adam/FusedAdam；big_leaf 不在其参数列表中。因此，手工普通优化器测得的 16→2 参数
收益不能直接套到正式入口，每 rank 的实际 shard 数和 optimizer 开销需单独测量。

**big_leaf 刻意没拿的两项 pin 收益：**

1. 不拿 eval 场景的 pin 缓存命中收益，因为 plain tensor 每次都 fresh pack；
2. 不拿 `memory_efficient=True` 的潜在显存节省。B6 在 8192×4096 fast FC
   线性层实测为 bf16 224MiB、fp32 448MiB，但不能把这个数直接当作当前 MoE
   shape 的显存差。

「没拿 pin 显存收益」与「big_leaf apply 显存中性」不矛盾：C9 的 <1MiB 断言只
衡量 **repack 后权重常驻显存**，不衡量 forward 内部 fresh pack workspace。
apply 复制期间仍有单层瞬时 2× 峰值；MoE 运行期 fresh pack 的精确峰值差尚未
单独测量。

### 6.5 「每步失效重 pack」与 B12 风险的完整因果链

LW=1 训练态的时间线是：

| 时点 | 行为 |
|---|---|
| 第 N 步 forward | Parameter 进入 pin 路径，使用或建立 packed cache |
| 第 N 步 backward + optimizer.step | 权重被更新，旧 packed cache 不再代表新权重 |
| optimizer step post-hook | 原 XME 或当前 TTorch 生命周期调用 `reinitialize_all_after_param_update`，使 stateful cache 失效 |
| 第 N+1 步 forward | 读取更新后的 large_weight，重新 pack；由此产生独立测得的约 112-160us 成本 |

**B12 不是 big_leaf 的 bug，而是 fast FC stateful cache 的生命周期依赖。**
完整模型 harness 已实测：裸链路没有 XME/TTorch wrapper 管理时，fast FC +
optimizer.step 后会因陈旧 cache 出现 NaN；in-process `load_state_dict` 也不会
自动使 cast cache 失效，需要手动 reinitialize。

big_leaf 的 big_leaf 权重因为不是 Parameter，不走 pin cache；每次 forward
fresh pack 都读取当前 buf，所以**这一个权重不再依赖 post-hook 才能看到新值**。
整网其他 Parameter 仍需要生命周期管理：最终显式总开关入口默认安装 TTorch
optimizer-step/save/load patches，并强制 BF16 pin 关闭，因此不再依赖 XME；
绕过正式入口的裸链路仍保留上述风险。

#### 6.6.1 终版模块级与整网级对比

模块级来源：`bench_final_comparison.py`，fast FC 开、
`XTE_USE_GROUPED_FC_FUSION=0`、bf16、8K tokens、fwd+bwd+step、生产 TE

|---|---:|---:|---:|---:|---|
| G8 2048→1536 无 bias | 2716 | 2685 (1.012x) | 2434 (1.116x) | **2413 (1.126x)** | 快约 21us |
| G8 2048→1536 有 bias | 3301 | 3299 (1.001x) | 2673 (1.235x) | **2645 (1.248x)** | 快约 27us |

**关键口径限制：**`bench_final_comparison.py` 的模块级 step 没有调用 XME

也不是 DistributedOptimizer 对比。§6.5 的 112-160us 是独立微基准，
**不能再机械加到上表 LW=1 数字上**。

这些表仅用于手工普通优化器/裸链路的方案归因，**不能证明正式
DistributedOptimizer 入口下 big_leaf 与 LW=1 净性能相同**。正式入口当前只有
stock/big 的三轮 200 步结果（§9.5），尚缺 stock/LW=1/big_leaf 同模型、同并行、
同 optimizer 与同生命周期的三方对比。

#### 6.6.2 归因数据：optimizer 与 pin/repack

G=8、weight+bias、16 参数 vs 2 参数的孤立 optimizer 测量：

| optimizer | 16 参数 | 2 参数 | 多参数差 |
|---|---:|---:|---:|
| 普通 TE FusedAdam | 772us | 610us | 162us |
| torch fused AdamW | 791us | 614us | 177us |
| torch foreach AdamW | 1891us | 1378us | 513us |
| apex FusedAdam | 1567us | 1538us | 29us |

因此「optimizer 合并省多少」没有跨实现固定答案。手工普通优化器可使用相同 TE
FusedAdam 口径；apex 在本栈绝对速度较慢，但 Megatron try 链实际优先 TE，不能把
apex 数字当成当前现状。DistributedOptimizer 还必须按每 rank 实际 shard 数测量，
不能直接引用这张普通 optimizer 孤立表。

pin 与 fresh pack 的独立 fwd+bwd 微基准（同 G8 shape）：

| 形态 | 时延 | 含义 |
|---|---:|---|
| plain/view，每步 fresh pack | 1910us | big_leaf 所属的 kernel 输入类型 |
| Parameter pin + 每步显式失效重 pack | 2067us | 模拟生产训练态缓存生命周期 |
| 差值 | 约 157us | 另一轮/另一脚本记录为约 112us，故文档统一写约 112-160us |

另有缓存命中实验显示 Parameter/plain/view 约同速（约 1920us），证明不存在
稳定的「view kernel 慢路径惩罚」；真 cat 才是此前误判为视图惩罚的拷贝来源。

2026-11-09 审查修复后的最终复跑仍保持同向：big_leaf 在 foreach/fused/apex 下
分别为 1.183/1.129/1.062x，LW=1 分别为 1.175/1.118/1.055x。该轮包含新增
运行期防护，只用于确认回归方向，不替换 §6.6.1 的主基准。

### 6.7 工程兼容、易用性与代码内聚性对比

| 维度 | LW=1 | big_leaf：手工普通优化器 | big_leaf：DistributedOptimizer |
|---|---|---|---|
| 参数注册、模型 ckpt、HF | 改为 `large_weight`/`large_bias`，下游需翻译回 per-expert | 保持 `weight{i}`/`bias{i}`，模型键和 HF 导出是明确优势 | 同左 |
| 使能与回滚 | 建模时决定注册形态，切换通常需重建模型并转换权重 | 可在建模/load 后 apply；restore 恢复独立存储，但需重建 optimizer | DDP 边界自动装配；生产回滚优先新进程和 fully-reshardable ckpt |
| 普通 optimizer 构建 | `model.parameters()` 天然看到大 Parameter，**这一点更直接** | 必须使用 `optimizer_params()` / `optimizer_param_groups()`，grad clip 使用 `grad_tensors()`，**不如 LW=1 透明** | 禁止套用单机参数列表，继续原 `get_megatron_optimizer(DDP)` |
| optimizer 单实体收益 | 有 | 有 | **没有完整获得**；原 Parameter、DDP 元数据和本地 shard 映射仍在 |
| optimizer resume | 依赖 large/per-expert 键及索引转换补丁 | stock/LW=1→big、big→stock 仍需显式 `convert_optimizer_state_dict()`，并非无感 | fully-reshardable stock↔big 不调用普通 converter；LW=1 原生格式仍需先转 canonical |
| DistributedOptimizer | 依赖现有 large-weight 分片与 checkpoint 兼容链 | 不使用此路径 | canonical layout + main_grad flush；DP/EP/overlap 已验证，但每步 flush 是独立开销 |
| LoRA | 注册变化需属性 shim 和 merge/unmerge 写回 | 原参数名保留，仍需外部 `.data=` 重绑定守卫；不是完全无感 | 同左，另有 LoRA+DP2 验证 |
| pin / eval | eval/冻结可命中 pin cache，memory_efficient 有潜在显存价值 | plain tensor fresh pack，不拿这两项收益；训练时可避开 pin 重 pack 溢价 | 当前正式入口强制关闭 BF16 pin，同样不拿 |
| 代码所有权 | 存储在 XTE，分片/ckpt 在 XME，HF/LoRA 在 XSwift，职责跨包 | 主要集中在 `core.py` + `checkpoint.py`，但调用方仍要装配 optimizer/converter | 集中在 TTorch big_leaf 各模块，optimizer/checkpoint 逻辑复用框架原实现 |
| 主要短板 | 注册契约变化、L0-L8 shim、ckpt 索引与格式风险 | 显式 optimizer/grad clip/converter 集成；禁止 assign 和动态 freeze；仍依赖 TE 私有 forward/kernel | optimizer 单实体收益缺失、main_grad flush、DDP 配置限制；并非所有 ckpt 格式天然兼容 |
| 性能证据边界 | 有模块级和裸整网对比 | 当前口径下与 LW=1 持平或略优，仅限手工/裸链路 | 仅有对 stock 的正式 3×200 步正收益，**没有对 LW=1 的同环境净性能结论** |

### 6.8 总评：差异化优势不是“全面无感”或“全面反超”

1. **手工普通优化器路径**：完整保留 forward、backward 和 optimizer 单实体三类
   主要性能机制，现有模块级/裸整网数据与 LW=1 持平或略优。其差异化优势是 stock
   模型键、建模后 apply/restore、集中的代码所有权；劣势是普通 optimizer 构建、
   grad clip 和 optimizer resume 反而比 LW=1 更需要显式适配。
2. **DistributedOptimizer 正式入口**：保留 forward host/cat 和主要 backward 收益，
   以不完整获得 optimizer 单实体与 DDP 元数据缩减收益为代价，复用原
   DistributedOptimizer/checkpoint 逻辑契约。它不是“完整 LW=1 性能机制的无侵入复制”。
3. **big_leaf 相对 LW=1 的真实工程优势**：模型注册和 HF 契约不分叉、可在建模后
   启用、兼容逻辑集中在 TTorch，而不是散落 XTE/XME/XSwift。内聚性不等于零修改，
   LoRA/load 守卫、DDP layout、main_grad 和手工 converter 仍是明确的感知点。
4. **LW=1 的相对优势**：普通 optimizer 可直接消费 `model.parameters()`，在
   DistributedOptimizer 中也天然是单注册参数；eval 可命中 pin cache，且存量 L0-L8
   已稳定时没有新增迁移成本。其代价仍是跨包 shim 和 ckpt 格式/索引风险。
5. **最终证据边界**：正式入口的 3×200 步结果只证明 big_leaf 对 stock 有稳定正收益。
   在同模型、同 DistributedOptimizer、同 TE FusedAdam、同 fast-FC/cache 生命周期下
   完成 stock/LW=1/big_leaf 三方 fwd+bwd+step 对比之前，不宣称生产净性能追平或反超
   LW=1。是否选用 big_leaf，主要取决于 XME/XSwift 退役和 stock 模型契约价值，
   而不是一个尚未测得的全面性能结论。

### 7.3 排查中修正的测试口径

- EP 的 main_grad 不能只拿本地 stock `.grad` 比较：必须按 bucket 的

## 9. TTorch 正式入口与生产闭环（2026-11-09 第三轮）

### 9.1 高内聚、低耦合落地

- `ttorch/bridge/big_leaf/core.py`：只负责模块存储、autograd 叶子、forward 与 restore；
- `megatron.py`：只负责 canonical DDP layout、main_grad flush 和 DistributedOptimizer
  参数/shard 契约衔接；
- `checkpoint.py`：只负责手工普通 optimizer/model-space 的 stock/big state 双向转换，
  不在正式 DistributedOptimizer 自动入口调用；
- `runtime.py`：只负责 DDP 构造边界；`lifecycle.py`：只负责 optimizer-step、save/load
  生命周期；`swift.py`：只负责 CLI 装配和 applied 校验；计时独立在
  `ttorch/witness/step_timer.py`。默认未设置 trace 时不增加设备同步。
- 公共 API 通过 `ttorch.bridge.big_leaf` 惰性导出，不把 TE/Megatron 依赖扩散到普通
  TTorch 进程。正式 CLI 为 `python -m ttorch.bridge.big_leaf.swift sft ...`，安装后
  逐点检查 `applied`，禁止 pending 静默通过。

这里的“高内聚”指 stock 模型契约和 big_leaf 特有逻辑有单一所有者，不代表所有外部
流程无感：手工普通 optimizer 的构造/grad clip/converter，以及 LoRA/load 守卫、
动态冻结限制、DDP layout 和 main_grad flush 仍是显式边界。

## 11. patch 直调 GEMM custom-op：方案分析与暂缓决策（2026-11-10）

### 11.1 决策

**当前不修改实现，不纳入本次 big_leaf PR。** 保留现有 `patch` 路径；只有后续真实训练
profiling 证明中间 autograd/forward 包装是关键路径上的可恢复开销，才启动直调
custom-op 优化。该事项在待办总览登记为 **B13**，不是当前已确认的性能缺陷。

### 11.2 当前链路与剩余优化空间

当前 BF16 fast-FC 的 `patch` 路径已经绕过原 `GroupedLinear.forward` 的权重收集、
`noop_cat` 和原 LW switch，调用关系为：

```text
_big_leaf_forward
  → MoeFcFusionImpl.apply（即 _GroupedLinear）
  → hydrax GroupedLinearFunction
  → hydrax.moe_fc_fusion 等厂商算子
```

所谓“直调 custom-op”，是改为自有 `autograd.Function` 直接调用
`hydrax.moe_fc_fusion` 及 dgrad/wgrad 接口。它**不更换 GEMM kernel，也不改变 big_leaf
权重布局**；big_leaf 已获得的 host 收集、反向梯度拆分和 optimizer 参数数收益不会因
此再获得一次。剩余空间仅是中间包装的分派、上下文建立和可能的 host 间隙，收益必须
由 fwd+bwd 整网 profiling 证明，不能从接口层数推断。

`switch` 与本事项无关：它只是底层研究 API 中把 big_leaf 交给厂商 large-weight
forward 分支的兼容方式；生产已固定 `patch`，不提供 switch 环境配置，也不依赖该私有开关。

### 11.3 启动门槛与 profiling 证据

启动前必须在真实目标模型、目标 shape 和生产 dtype 上采集 train forward+backward trace，
并同时满足：

1. trace 能将 `_GroupedLinear` / `GroupedLinearFunction` 包装与实际 device kernel
   时间分开，证明待消除的是包装/调度开销，而非再次统计已经绕过的 `noop_cat`、权重收集；
2. 对应 host 时间或 host-device 空隙位于关键路径，而不是被异步 device 执行掩盖；
3. 开销在目标 ranks 和多轮 profile 中稳定复现，并能换算为整网 `train_step` 的可恢复
   收益；建议立项门槛为 **≥1% 整网步耗时**，未达门槛不增加私有接口耦合；
4. 性能判断必须覆盖 fwd+bwd。forward-only 自时间、单个 kernel 倍率或 Python 函数调用
   次数均不足以触发实现。

建议保留的原始证据：rank0 与代表 rank 的 trace、模块 shape/调用次数、host self-time、
stream 间隙、device kernel 时间，以及同配置 stock/big 的 `train_step` 中位数。

### 11.4 触发后的实施方案与工作量

首版严格限定当前已验收口径：BF16 + fast-FC、grouped fusion 关闭、无 int8/fp8、无
delayed-wgrad；不得借该优化顺带扩张 PP/VPP/FSDP/compile 支持范围。

| 阶段 | 内容 | 预估 |
|---|---|---:|
| P0 | profiling 定界与可恢复收益测算；未过 §11.3 门槛即停止 | 视真实 trace 而定 |
| P1 | forward-only PoC：`m_splits→lod`、输出/bias/reshape、fresh-pack 语义对拍 | 0.5–1 人日 |
| P2 | 自有 `autograd.Function`：fwd、dgrad、大叶子 wgrad、db、冻结/输入梯度与上下文 | 2–3 人日 |
| P3 | 复用现有核心、DDP/TP/EP、LoRA、checkpoint/resume 和真实生产回归 | 2–4 人日 |

达到当前 `patch` 的 PR 级覆盖预计合计 **5–8 人日**；代码量不是主要成本，反向语义和
验证才是。当前 `GroupedLinearFunction` 与 `hydrax.moe_fc_fusion` 位于编译 `.so`，缺少
可直接沿用的 Python 源码及完整参数文档，实施时需增加 ABI/版本探测并对未知形态
fail-fast，不能静默回退后仍宣称走了直调路径。

### 11.5 触发后的验收要求

- 固定 BF16 配置下，forward 输出及 `dx/dw/db` 与当前 `MoeFcFusionImpl` 路径逐位对拍；
  覆盖训练/评估、输入梯度、冻结 base、bias、空专家和零长度分片；
- 保持 big_leaf 梯度只归集到大叶子一次，DDP canonical layout、optimizer 参数组与
  checkpoint 键不变；各自 uninterrupted-vs-resume 仍逐位一致；
- 在相同模型、初始权重、数据与并行配置下做至少三轮交替性能测试，沿用 200 步、
  去 20 步 warmup、rank0 设备同步 `train_step` 中位数口径；
- 若精度不等价、整网收益未达到立项门槛或私有接口成本超过收益，保留现有实现并关闭
  B13，不因已投入 PoC 而继续合入。
